A13. Xulosa, test va suhbat mashqi

Bo'limning hamma narsasi bitta sahifada: har bir darsning asosiy fikri, bilish shart bo'lgan faktlar, tuzoqlar, barcha atamalar, barcha suhbat savollari javoblari bilan, katta test va suhbatning o'zini mashq qilish rejasi.

Bu nima

Android bo'limining yakuniy sahifasi. Yangi mavzu yo'q: A1–A12 darslarida batafsil va sxemalar bilan o'tilgan narsa ixcham ko'rinishda yig'ilgan, va ustiga suhbatga tayyorlanish qismi qo'shilgan.

Qayerda ishlatiladi

  • Bo'limni tugatganda: hammasi joyiga tushganini test bilan tekshirish.
  • Suhbatdan 1–2 kun oldin: xulosalar va suhbat savollarini takrorlash, o'zingizni tanishtirishni ovoz chiqarib mashq qilish.
  • Suhbat kuni ertalab: «Eslab qolish kerak bo'lgan faktlar» jadvali va oxirgi cheklist.

Maqsad

Testda har bir darsdan kamida 70%. Past chiqqan darsni qayta o'qing va faqat shu dars bo'yicha testni takrorlang.

Test tanishni tekshiradi, suhbat esa tushuntira olishni. Shuning uchun «Suhbat savollari» qismidagi har bir savolga javobni avval o'zingiz ovoz chiqarib ayting, keyin namunaviy javobni oching.

Sahifada

  1. Bo'lim bitta chizmada
  2. Darslar bo'yicha xulosa
  3. Eslab qolish kerak bo'lgan faktlar va versiyalar
  4. Barcha atamalar (151 ta)
  5. Suhbat savollari va namunaviy javoblar (92 ta)
  6. Mustahkamlash testi (120 ta savol)
  7. Suhbat mashqi
  8. Og'zaki tekshiruv savollari (60 ta)

Bo'lim bitta chizmada

O'n ikki dars bitta ilova qavatlariga joylashadi. Pastda til va runtime: Kotlin, funksiyalar, coroutines. Ustida ma'lumot manbalari: tarmoq va lokal baza. Keyin repozitoriy, domain va ViewModel, eng tepada Compose ekrani va navigatsiya. Uchta mavzu bitta qavatga sig'maydi va hammasini kesib o'tadi: DI (qismlarni kim yaratadi va ulaydi), Firebase va Git (ilova atrofidagi xizmatlar va jamoa ishi), xavfsizlik (har qavatda o'z himoyasi).

Darsni tanlang: chizmada u qaysi qavatda ishlashi va qaysi tushunchalari qayerga tegishi ajratiladi, pastda esa dars mazmuni bir gapda.

Darslar bo'yicha xulosa

Har dars uch qismda: bir xatboshida asosiy fikr, bilish shart bo'lgan faktlar va amaliyotdagi tuzoqlar. Suhbatda savolga javob berganda xuddi shu tartibda gapiring: nima, qanday ishlaydi, qanday xatoga olib keladi.

A1Kotlin va Java

Kotlin JVM baytkodiga (Android'da keyin DEX ga) kompilyatsiya qilinadi va Java bilan to'liq aralashadi. Farq tilda va kompilyatorda: null xavfsizligi tur tizimida, kamroq qolip kod, data class, kengaytmalar, coroutines. Ko'p qulayliklar ichkarida oddiy Java kodi.

Bilish shart

  • Yo'l. Kotlin va Java manbasi → kotlinc/javac → .class baytkod → D8 → DEX → telefonda ART (AOT va JIT). R8 kodni qisqartiradi va nomlarni chalkashtiradi.
  • Turlar. Kotlin'da hamma narsa obyekt ko'rinishida, lekin Int kompilyatsiyada primitiv int ga aylanadi. Int?, generiklar (List<Int>) va Any ichida qutilangan Integer.
  • Tenglik. == strukturaviy (equals), === havola. Qutilangan sonlarda −128..127 keshlangan, shuning uchun === kichik sonlarda tasodifan true.
  • Null xavfsizligi. String va String? har xil tur. ?., ?:, smart cast. Teshiklar: !!, lateinit, Java'dan kelgan platforma turi (String!).
  • data class. equals, hashCode, toString, copy, componentN ni faqat asosiy konstruktordagi xususiyatlardan yasaydi.
  • object va companion object. Singleton va klassga tegishli a'zolar; Java'da static yo'q, @JvmStatic bilan chiqariladi.
  • sealed. Cheklangan ierarxiya: when hamma holatni qamraganini kompilyator tekshiradi. Natija, xato, ekran holati uchun.
  • Any, Unit, Nothing. Hamma turning otasi; «qiymat yo'q» degan yagona obyekt; hech qachon qaytmaydigan ifoda turi (throw, TODO()).
  • val va var. val havolani o'zgartirib bo'lmaydi, obyektning ichi o'zgarishi mumkin. const val kompilyatsiya vaqtidagi doimiy.

Tuzoqlar va qoidalar

  • !! null xavfsizligini o'chiradi: NPE qaytadi. O'rniga ?: bilan aniq qaror.
  • data class ni HashSet/HashMap kaliti qilib, keyin o'zgaruvchan maydonini o'zgartirsangiz, obyekt to'plamda «yo'qoladi»: hashCode boshqa.
  • Kengaytma funksiya statik: qaysi funksiya chaqirilishi o'zgaruvchining e'lon qilingan turiga qarab, obyektning haqiqiy turiga emas. U klass ichidagi a'zoni yopmaydi.
  • Java'dan kelgan qiymat platforma turi: Kotlin uni tekshirmaydi. Chegarada darhol nullable yoki non-null deb aniq e'lon qiling, Java tomonda @Nullable/@NonNull.

A1 darsini to'liq ochish

A2Funksiyalar: lambda, inline, crossinline

Funksiya Kotlin'da qiymat: uni o'zgaruvchiga qo'yish, parametr qilib berish va qaytarish mumkin. Lambda ichkarida obyekt. inline kalit so'zi funksiya va lambda tanasini chaqirilgan joyga ko'chiradi: obyekt yaratilmaydi, lokal bo'lmagan return va reified ishlaydi.

Bilish shart

  • Lambda nimaga aylanadi. Function1 kabi interfeysni amalga oshiruvchi obyekt. Tashqi o'zgaruvchini ushlamasa bitta nusxa qayta ishlatiladi, ushlasa har chaqiruvda yangi obyekt; var ushlansa Ref qutiga o'raladi.
  • inline. Kompilyator funksiya tanasini va lambda kodini chaqiruv joyiga qo'yadi. Foydasi: obyekt yo'q, return tashqi funksiyadan chiqadi (lokal bo'lmagan qaytish). Narxi: kod hajmi o'sadi; katta funksiyalar uchun emas.
  • noinline. inline funksiyaning bitta lambda parametri ko'chirilmasin, obyekt bo'lib qolsin: uni saqlash yoki boshqa funksiyaga berish kerak bo'lganda.
  • crossinline. Lambda ko'chiriladi, lekin u boshqa kontekstda (boshqa lambda, obyekt, Runnable) chaqirilgani uchun undan lokal bo'lmagan return taqiqlanadi.
  • reified. Faqat inline funksiyada: tur parametri ish paytida ma'lum bo'ladi (T::class, is T), chunki chaqiruv joyida aniq tur qo'yiladi. Oddiy generiklarda tur o'chiriladi (type erasure).
  • Yorliqli qaytish. return@forEach faqat lambdadan chiqadi, keyingi elementga o'tadi.
  • Scope funksiyalar. let (it, natija), run (this, natija), with (this, natija, kengaytma emas), apply (this, obyektning o'zi), also (it, obyektning o'zi).
  • Qabul qiluvchili lambda. T.() -> Unit: lambda ichida this bu T. Compose va DSL lar (buildString, Koin module {}) shunga qurilgan.
  • fun interface. Bitta abstrakt metodli Kotlin interfeysi uchun SAM konversiya: lambda bilan amalga oshirish.

Tuzoqlar va qoidalar

  • forEach ichidagi oddiy return butun funksiyadan chiqadi, chunki forEach inline. Faqat elementni o'tkazib yuborish uchun return@forEach.
  • Lambda Activity yoki View'ni ushlab, uzoq yashovchi obyektda (singleton, statik ro'yxat) saqlansa, xotira oqadi.
  • Scope funksiyalarni zanjir qilib, ichma-ich it/this ishlatish kodni o'qib bo'lmas qiladi. Bitta maqsad, bitta scope funksiya.

A2 darsini to'liq ochish

A3Coroutines

Coroutine to'xtatib turilishi va keyin davom ettirilishi mumkin bo'lgan hisoblash. Kutish paytida u oqimni bo'shatadi. suspend funksiya kompilyatorda holat mashinasiga aylanadi; oqimni dispetcher tanlaydi. Coroutine'lar daraxt hosil qiladi va bekor qilish hamda xatolar shu daraxt bo'ylab tarqaladi.

Bilish shart

  • Asosiy oqim va ANR. UI bitta asosiy oqimda chiziladi. Asosiy oqim taxminan 5 soniya javob bermasa, tizim «Ilova javob bermayapti» (ANR) oynasini ko'rsatadi.
  • suspend ichkaridan. Kompilyator har bir suspend funksiyaga yashirin Continuation parametrini qo'shadi va tanani to'xtash nuqtalari bo'yicha holat mashinasiga bo'ladi. To'xtaganda funksiya COROUTINE_SUSPENDED qaytaradi va oqim bo'shaydi.
  • Builderlar. launch: natijasiz, Job qaytaradi. async: natijali, Deferred qaytaradi, await() bilan olinadi. runBlocking: oqimni bloklaydi, faqat test va main uchun. withContext: dispetcherni almashtirib, natijani qaytaradi.
  • Dispetcherlar. Main (UI), IO (bloklovchi kirish-chiqish, 64 tagacha oqim), Default (hisoblash, yadrolar soni), Unconfined (maxsus holatlar).
  • Scope va kontekst. CoroutineScope hayot muddati chegarasi; CoroutineContext bu Job + dispetcher + nom + xato ushlagich. Android'da viewModelScope (SupervisorJob + Dispatchers.Main.immediate) va lifecycleScope.
  • Tuzilmaviy parallellik. Ota-ona bekor qilinsa bolalar ham bekor bo'ladi; bola xato bersa ota-ona va aka-ukalari bekor bo'ladi. SupervisorJob / supervisorScope da bola xatosi boshqalarga tarqalmaydi.
  • Bekor qilish hamkorlikda. Coroutine to'xtash nuqtalarida yoki isActive, ensureActive() tekshiruvida to'xtaydi. Bekor qilish CancellationException orqali ishlaydi.
  • Xatolar. launch da xato ota-onaga tarqaladi va CoroutineExceptionHandler gacha boradi; async da await() da otiladi. Main-safe funksiya: istalgan oqimdan chaqirish xavfsiz, ichida o'zi withContext qiladi.
  • Test. runTest (virtual vaqt), StandardTestDispatcher, Dispatchers.setMain; dispetcherlarni DI orqali berish.

Tuzoqlar va qoidalar

  • GlobalScope hech kimga bog'lanmagan: ekran yopilsa ham ishlaydi, xotira va trafik oqadi. Har doim hayot muddatiga bog'langan scope.
  • runCatching va catch (e: Exception) CancellationException ni ham yutadi va bekor qilingan coroutine ishlashda davom etadi. Uni qayta otish kerak.
  • suspend so'zi kodni fon oqimiga o'tkazmaydi. Og'ir hisob withContext(Dispatchers.Default), bloklovchi I/O withContext(Dispatchers.IO). Thread.sleep emas, delay.
  • Parallel so'rovlar: coroutineScope { async {}; async {} }. Biri xato bersa ikkinchisi bekor bo'ladi. Mustaqil natijalar kerak bo'lsa supervisorScope.

A4Flow: StateFlow va SharedFlow

Flow vaqt bo'ylab keladigan qiymatlar oqimi, coroutine'lar ustiga qurilgan. Oddiy flow sovuq: har bir kollektorga alohida ishlaydi. ViewModel ekranga issiq oqim beradi: holat uchun StateFlow, bir martalik hodisalar uchun Channel yoki SharedFlow. Ekran oqimni hayot siklini hisobga olib kuzatadi.

Bilish shart

  • Sovuq va issiq. Sovuq (flow {}): collect chaqirilganda boshlanadi, har kollektorga o'z nusxasi. Issiq (StateFlow, SharedFlow): kollektordan qat'i nazar mavjud, hammaga bir xil qiymat.
  • Operatorlar. Oraliq (map, filter, debounce, flatMapLatest, combine, flowOn) oqimni o'zgartiradi va hech narsani ishga tushirmaydi. Terminal (collect, first, toList) ishga tushiradi, suspend.
  • StateFlow. Doim qiymati bor (value), oxirgisini yangi kollektorga beradi, tengini qayta chiqarmaydi (equals), oraliqlarni tashlab yuboradi (conflation). Holat uchun.
  • SharedFlow. Boshlang'ich qiymatsiz, replay va bufer sozlanadi. Hech kim kuzatmayotganda chiqarilgan qiymat yo'qoladi (replay = 0).
  • Channel. Har qiymat bitta oluvchiga; oluvchi yo'q bo'lsa buferda kutadi. Bir martalik hodisalar (navigatsiya, xabar) uchun ishlatiladi; Google tavsiyasi esa hodisani holatga aylantirish.
  • stateIn va shareIn. Sovuq oqimni issiqqa aylantiradi. SharingStarted.WhileSubscribed(5000): oxirgi kollektor ketgandan keyin 5 soniya kutib to'xtaydi; ekran burilganda qayta yuklanmaydi.
  • Kuzatish. Compose'da collectAsStateWithLifecycle(), View'da repeatOnLifecycle(STARTED): ilova fonda bo'lganda kuzatish to'xtaydi.
  • Xato va kontekst. catch faqat o'zidan yuqoridagi xatoni ushlaydi. flowOn faqat o'zidan yuqoridagi qismlarning dispetcherini o'zgartiradi.

Tuzoqlar va qoidalar

  • Sovuq oqimni ikki joyda kuzatish so'rovni ikki marta yuboradi. Bitta issiq oqim qiling (stateIn, shareIn).
  • Holat ichidagi o'zgaruvchan ro'yxatni o'zgartirib, o'sha obyektni qayta qo'ysangiz, StateFlow uni teng deb chiqarmaydi. O'zgarmas data class va _state.update { it.copy(...) }.
  • catch kollektor (collect { }) ichidagi xatoni ushlamaydi: u quyi oqimda. Mantiqni onEach ga olib, catch dan oldin qo'ying.
  • MutableStateFlow tashqariga chiqmasin: private _state va ochiq state: StateFlow (asStateFlow()).

A4 darsini to'liq ochish

A5Arxitektura: Clean, SOLID, MVI

Arxitektura o'zgarishni xavfsiz qilish uchun: ekranni, biznes qoidalarni va ma'lumot manbalarini ajratadi. Clean Architecture'da bog'liqlik faqat ichkariga, domain tomonga qaraydi. MVI'da ekran bitta o'zgarmas holatni ko'rsatadi, foydalanuvchi niyat yuboradi, reduktor yangi holat hisoblaydi.

Bilish shart

  • Qavatlar. Presentation (Compose, ViewModel), domain (use case, model, repozitoriy interfeysi; Android'siz toza Kotlin), data (repozitoriy amalga oshirilishi, API, baza, DTO, mapper).
  • Bog'liqlik qoidasi. Domain hech kimni bilmaydi. Data domain'dagi interfeysni amalga oshiradi: bog'liqlik teskari aylantirilgan (DIP).
  • Modellar. DTO (serverdagi JSON shakli), Entity (baza jadvali), domain modeli (biznes tushunchasi), UI modeli (ekranga tayyor matn). Mapper ular orasida.
  • SOLID. S: bitta o'zgarish sababi. O: kengaytirishga ochiq, o'zgartirishga yopiq. L: voris otaning o'rnini to'liq bosadi. I: kichik, aniq interfeyslar. D: abstraksiyaga bog'liq bo'ling.
  • MVC → MVP → MVVM → MVI. Activity hamma narsani qiladi → Presenter interfeys orqali View'ni boshqaradi → ViewModel kuzatiladigan holat beradi va View'ni bilmaydi → bitta holat, niyatlar, reduktor.
  • MVI qismlari. State (o'zgarmas data class), Intent (sealed: foydalanuvchi nima qilmoqchi), Reducer ((state, natija) -> yangi state, sof funksiya), Effect (bir martalik: navigatsiya, toast).
  • UDF. Ma'lumot bir yo'nalishda: holat pastga (ekranga), hodisalar yuqoriga (ViewModel'ga). Har bir holat o'zgarishini bitta joyda kuzatish va qayta ishlab chiqish mumkin.
  • Jarayon o'limi. Tizim fondagi ilovani o'ldirishi mumkin; ViewModel yo'qoladi. Muhim holat SavedStateHandle da.

Tuzoqlar va qoidalar

  • ViewModel ichida Activity Context yoki View: burilishda xotira oqadi. Resurs kerak bo'lsa ekranga ID beriladi yoki Application Context.
  • Har bir repozitoriy chaqiruvini use case'ga o'rash: mantiqsiz qatlam. Use case qoida bor joyda yoki bir nechta repozitoriy birlashganda.
  • Holatga bir martalik hodisa qo'yish: burilishda toast qayta chiqadi. Hodisa effekt kanalida yoki ishlov berilgach holatdan tozalanadi.
  • Jarayon o'limini unutish: foydalanuvchi qaytganda forma bo'sh. SavedStateHandle va lokal baza.

A6Dependency Injection: Hilt va Koin

Dependency Injection: klass o'ziga kerak narsani o'zi yaratmaydi, konstruktorda oladi. Kim yaratadi va qancha yashaydi, buni bitta joy, DI konteyner hal qiladi. Hilt (Dagger) grafni kompilyatsiyada tekshirib kod yaratadi; Koin Kotlin DSL bilan ish paytida topadi.

Bilish shart

  • Nega kerak. Testda soxta bog'liqlik berish, almashtirish (test va real server), yashash muddatini boshqarish, bog'lanishni kamaytirish.
  • DI va Service Locator. DI'da bog'liqlik tashqaridan beriladi; Service Locator'da klass o'zi «ber» deb so'raydi (get()). Koin ikkalasini ham qila oladi; to'g'ri ishlatish: konstruktor orqali.
  • Koin. module { single { } ; factory { } ; viewModel { } }, get(), startKoin. Koin 4: singleOf(::Klass), viewModelOf, koinViewModel() Compose'da, Kotlin Multiplatform. Koin Annotations kompilyatsiyada tekshirish ham beradi.
  • Hilt. @HiltAndroidApp, @AndroidEntryPoint, @HiltViewModel, @Inject constructor, @Module @InstallIn(SingletonComponent::class), @Provides (o'zingiz yaratasiz), @Binds (interfeysni amalga oshirishga bog'lash). KSP/kapt bilan kod yaratadi.
  • Yashash muddati. single/@Singleton: ilova davomida bitta. factory: har so'rovda yangi. viewModel: ViewModel hayot sikli. Scope (Activity, ekran, sessiya) oraliq muddatlar uchun.
  • Qualifier. Bir xil turdagi ikki bog'liqlikni ajratish: named("auth") Koin'da, @Named yoki o'z annotatsiyasi Hilt'da.
  • Taqqoslash. Hilt: xato kompilyatsiyada, tez ish vaqti, ko'proq qolip va sekinroq yig'ish. Koin: oddiy, tez yig'ish, KMP; xato ish paytida, shuning uchun verify() yoki checkModules testi.

Tuzoqlar va qoidalar

  • Koin'da e'lon qilinmagan bog'liqlik faqat ekran ochilganda qulashni beradi. Har modulni CI'da verify testi bilan tekshirish.
  • ViewModel'ni factory yoki single bilan berish: hayot sikli buziladi, burilishda holat yo'qoladi yoki ekranlar orasida aralashadi. Faqat viewModel / @HiltViewModel.
  • Singleton'ga Activity Context berish: Activity yopilganda ham xotirada qoladi. Singleton'larga faqat Application Context.
  • Bog'liqliklar konstruktorda; get() va inject() faqat chegarada (Activity, composable kirish nuqtasi).

A7Jetpack Compose

Compose deklarativ: siz holatga qarab UI qanday ko'rinishini yozasiz, holat o'zgarsa Compose shu holatni o'qigan qismlarni qayta chaqiradi (rekompozitsiya). Parametrlari o'zgarmagan barqaror composable'lar o'tkazib yuboriladi. Holat yuqoriga ko'tariladi, yon ta'sirlar faqat effekt API lari orqali.

Bilish shart

  • Uch bosqich. Kompozitsiya (nima chiziladi), joylashtirish (o'lchash va joy), chizish. Holat qaysi bosqichda o'qilsa, shu bosqichdan boshlab qayta ishlanadi.
  • @Composable. Kompilyator plagini funksiyaga Composer parametrini qo'shadi; Compose daraxtni slot jadvalida saqlaydi va funksiyani istalgan tartibda, istalgancha chaqira oladi: tana tez va yon ta'sirsiz bo'lishi kerak.
  • Holat. mutableStateOf kuzatiladigan qiymat; remember uni rekompozitsiyalar orasida saqlaydi; rememberSaveable burilish va jarayon o'limidan keyin ham.
  • Barqarorlik. O'zgarmas turlar (val, primitivlar, String, @Immutable/@Stable) barqaror. Kotlin 2.0.20 dan kuchli o'tkazib yuborish sukut bo'yicha yoqilgan: beqaror parametrlar ham havola tengligi bilan solishtiriladi, lambdalar avtomatik eslab qolinadi.
  • Holatni ko'tarish. Composable holatsiz: value va onValueChange oladi. Ekran holati ViewModel'da, faqat UI elementi holati (ochiq/yopiq) composable'da.
  • derivedStateOf. Tez o'zgaradigan holatdan kamroq o'zgaradigan natija (masalan, ro'yxat 0-elementdan o'tdimi): rekompozitsiyani kamaytiradi.
  • Effektlar. LaunchedEffect(key): kalit o'zgarsa coroutine qayta boshlanadi. DisposableEffect: tozalash bilan. rememberCoroutineScope: bosish ichida coroutine. SideEffect, rememberUpdatedState, produceState.
  • Ro'yxat. LazyColumn faqat ko'rinadiganlarni yaratadi; items(list, key = { it.id }) element o'rni o'zgarsa holatini saqlaydi.
  • CompositionLocal. Daraxt bo'ylab yashirin uzatiladigan qiymat (mavzu, kontekst). Kam o'zgaradigan narsalar uchun, oddiy parametr o'rniga emas.

Tuzoqlar va qoidalar

  • Composable tanasida tarmoq so'rovi yoki og'ir hisob: har rekompozitsiyada qayta ishlaydi. So'rov ViewModel'da, hisob remember yoki derivedStateOf bilan.
  • LaunchedEffect(Unit) ichida o'zgaradigan parametr ishlatilsa, eski qiymat bilan qoladi. Kalit qiling yoki rememberUpdatedState.
  • Ro'yxatda key yo'q: element qo'shilganda yoki o'chirilganda holat boshqa qatorga o'tib ketadi, animatsiyalar buziladi.
  • Tez o'zgaradigan holatni (skroll, animatsiya) kechiktirib o'qing: lambda (Modifier.offset { }, graphicsLayer { }) faqat joylashtirish yoki chizishni qayta ishlatadi.

A8Navigatsiya: Compose Navigation va Navigation 3

Navigatsiya bu orqaga qaytish steki ustidagi amallar: qo'shish, olib tashlash, almashtirish. Navigation 2 (Compose) da stek NavController ichida yashirin. Navigation 3 (1.0 barqaror, 2025-yil noyabr) da stek sizning oddiy holatingiz: ro'yxat, NavDisplay uni ko'rsatadi.

Bilish shart

  • Navigation Compose. NavHost, NavController, composable<Route>. 2.8 dan tur xavfsiz marshrutlar: @Serializable klass yoki object, navigate(Detail(id)), toRoute<Detail>().
  • Stek amallari. popUpTo(Login) { inclusive = true }: kirish ekranini stekdan olib tashlash. launchSingleTop: bir xil ekranni ikki marta qo'shmaslik. saveState/restoreState: pastki menyu tablari.
  • NavBackStackEntry. Har bir yozuvning o'z hayot sikli, ViewModelStore va SavedStateHandle'i bor: ViewModel ekran yopilganda tozalanadi.
  • Navigation 3. NavKey (marshrut kaliti), rememberNavBackStack(Home) (saqlanadigan stek), NavDisplay(backStack, onBack, entryProvider), entryProvider { entry<Detail> { key -> } }. Navigatsiya: backStack.add(Detail(id)), orqaga: removeLastOrNull().
  • Dekoratorlar. rememberSaveableStateHolderNavEntryDecorator (har yozuvning saqlanadigan holati), rememberViewModelStoreNavEntryDecorator (har yozuvga o'z ViewModel'i; lifecycle-viewmodel-navigation3).
  • Sahnalar. SceneStrategy: katta ekranda ro'yxat va tafsilotni yonma-yon ko'rsatish, dialog va bottom sheet.
  • Chuqur havola. Tashqi havola (push, sayt) ilovaning ichki ekranini ochadi; Nav2 da deepLinks, Nav3 da Intent'ni o'qib, stekni o'zingiz qurasiz. Kirish tekshiruvi har doim.
  • Ichki graf. Bir nechta ekranlik oqim (o'tkazma: summa → tasdiq → natija) umumiy ViewModel bilan.

Tuzoqlar va qoidalar

  • Katta obyektni argument qilib berish: Bundle chegarasi va jarayon o'limida yo'qolish. Faqat ID, ma'lumot repozitoriydan.
  • ViewModel ichida NavController: xotira oqishi va testlab bo'lmaslik. ViewModel effekt chiqaradi, ekran navigatsiya qiladi.

A9Tarmoq: Retrofit, Ktor, tokenlar

Ilova server bilan HTTP orqali JSON almashadi. Retrofit interfeysdan so'rov yasaydi, OkHttp uni yuboradi va interceptor zanjiri orqali o'tkazadi; Ktor client xuddi shuni Kotlin Multiplatform'da qiladi. Xatolar repozitoriyda domain turlariga aylanadi, tokenlar bitta joyda yangilanadi.

Bilish shart

  • REST va HTTP. Resurs va metodlar: GET o'qish, POST yaratish, PUT/PATCH o'zgartirish, DELETE. Kodlar: 2xx muvaffaqiyat, 400 so'rov xato, 401 autentifikatsiya yo'q, 403 ruxsat yo'q, 404, 409 ziddiyat, 422, 429 juda ko'p, 5xx server.
  • Retrofit. interface Api { @GET("cards") suspend fun cards(): List<CardDto> }. suspend funksiyalar, Response<T> kod va tanani o'qish uchun, konverter (kotlinx.serialization, Moshi, Gson).
  • OkHttp. Ulanishlar havzasi, HTTP/2, kesh, taymautlar. Interceptor: so'rov va javobni o'zgartiradi (sarlavha, log, token). Authenticator: 401 kelganda chaqiriladi.
  • Ktor client. HttpClient(OkHttp) { install(ContentNegotiation) { json() } }; plaginlar: Auth (Bearer, refresh), Logging, HttpTimeout, retry. KMP da iOS bilan umumiy kod.
  • JSON. kotlinx.serialization: @Serializable, kompilyatsiyada kod yaratadi, reflection yo'q, Kotlin null va standart qiymatlarni tushunadi. ignoreUnknownKeys = true server yangi maydon qo'shsa qulamaslik uchun.
  • Xatolar. Tarmoq yo'q (IOException), taymaut, HTTP xato (kod va tanasi), JSON xato. Repozitoriy ularni sealed domain turiga aylantiradi; ekran foydalanuvchiga tushunarli xabar ko'rsatadi.
  • Tokenlar. Access token qisqa muddatli, har so'rovda Authorization: Bearer. Refresh token uzoq, faqat yangilash uchun. JWT: header.payload.signature, base64, shifrlanmagan.
  • Yangilash. 401 → Authenticator bitta qulf ostida bir marta yangilaydi, qolgan so'rovlar kutadi va yangi token bilan qayta yuboriladi. Refresh ham rad etilsa, chiqish.
  • Idempotentlik. Takrorlansa natija o'zgarmaydigan so'rov. Pul o'tkazmasi Idempotency-Key (UUID) bilan: server bir xil kalitni ikki marta bajarmaydi.

Tuzoqlar va qoidalar

  • Log interceptor BODY darajasida release'da: token va karta ma'lumotlari logda. Faqat debug, release'da NONE yoki maxfiy sarlavhalarsiz.
  • Har bir so'rov o'zi tokenni yangilaydi: bir vaqtda beshta refresh, server birinchisidan keyin qolganlarini rad etadi va foydalanuvchi chiqib ketadi.
  • To'lov so'rovini taymautdan keyin avtomatik qayta yuborish: ikki marta yechish. Qayta yuborish faqat idempotentlik kaliti bilan.
  • Server xatosining tanasini o'qimaslik: «Xatolik yuz berdi» o'rniga «Hisobda mablag' yetarli emas» ko'rsatilishi kerak.

A12Mobil bank xavfsizligi

Bank ilovasi foydalanuvchining telefonida ishlaydi va u sizning nazoratingizda emas. Shuning uchun mijozga ishonilmaydi: muhim qoidalar serverda. Ilovaning vazifasi: maxfiy ma'lumotni qurilmada shifrlab saqlash, tarmoqni himoyalash, foydalanuvchini tasdiqlash va hujum belgilarini serverga xabar qilish.

Bilish shart

  • Tahdid modeli. Kim (o'g'ri, zararli ilova, ochiq Wi-Fi, root qilingan qurilma egasi), nimaga (token, karta, PIN, ekran), qanday yo'l bilan. Himoya qavatlari: ekran, tarmoq, saqlash, ilova, qurilma butunligi, server.
  • Android Keystore. Kalit ilovadan tashqarida, ko'pincha apparat muhitida (TEE; Android 9 dan ba'zi qurilmalarda StrongBox chipi). Ilova kalitni ko'rmaydi, faqat u bilan amal so'raydi. Shartlar: ekran qulfi, biometriya.
  • Shifrlab saqlash. Tink AEAD (AES-256-GCM), Tink kalitlari Keystore kaliti bilan shifrlangan, natija DataStore'da. EncryptedSharedPreferences (security-crypto) 1.1.0 da eskirgan deb belgilangan.
  • TLS. Trafik shifrlanadi, server sertifikat bilan tekshiriladi. Android 7 dan ilovalar foydalanuvchi o'rnatgan CA larga sukut bo'yicha ishonmaydi; Android 9 dan ochiq HTTP sukut bo'yicha taqiqlangan. Network Security Config: domenlar, CA, pinlar, debug-overrides.
  • Pinning. Ilova server kalitining xeshini biladi va boshqasini rad etadi. Kamida ikkita pin (joriy va zaxira), muddat va almashtirish rejasi; aks holda sertifikat yangilanganda ilova ishlamay qoladi.
  • Biometriya. BiometricPrompt + CryptoObject: tasdiqlash Keystore kalitini ochadi. setUserAuthenticationRequired, setInvalidatedByBiometricEnrollment(true). Biometriya PIN ni qulaylashtiradi, o'rnini bosmaydi.
  • Butunlik. Play Integrity API: Google imzolagan xulosa (ilova, qurilma, hisob), uni server tekshiradi. SafetyNet Attestation 2025-yil yanvarida o'chirilgan. R8 kodni o'qishni qiyinlashtiradi, sir saqlamaydi.
  • Ilova sathi. FLAG_SECURE maxfiy ekranlarda, overlay himoyasi, buferga maxfiy belgi, exported faqat kerak bo'lsa, WebView'da faqat ishonchli domen, zaxira nusxadan chiqarish, release'da log yo'q, sessiya muddati.
  • Standart. OWASP MASVS (talablar) va MASTG (tekshirish qo'llanmasi): mobil ilova xavfsizligi auditi shular bo'yicha.

Tuzoqlar va qoidalar

  • Xavfsizlik faqat ilovada: limit, PIN urinishlari, root tekshiruvi ilovada bo'lsa, hujumchi ularni olib tashlaydi. Hammasi serverda.
  • Barcha sertifikatlarga ishonadigan TrustManager «vaqtincha» yozilib release'ga tushadi: har qanday MITM ochiq, Google Play rad etishi mumkin.
  • Ilovada sir (server API kaliti, imzolash kaliti): ilovadagi hamma narsa oxir-oqibat ochiq. Sirlar serverda.
  • Pinlarni rejasiz qo'yish: sertifikat almashganda hamma foydalanuvchida ilova ishlamay qoladi. Zaxira pin, muddat, masofadan o'chirish imkoni.

A1. Kotlin va Java (10 ta savol)

Avval javobni o'zingiz ovoz chiqarib ayting, keyin oching. Namunaviy javob yod olish uchun emas: undagi asosiy fikrlar sizning javobingizda bo'lishi kerak.

Kotlin Java'dan nimasi bilan farq qiladi?

Ikkalasi ham JVM baytkodiga kompilyatsiya qilinadi va bir-biri bilan to'liq mos ishlaydi. Asosiy farqlar: Kotlin'da null xavfsizligi tur tizimida (String va String?), Java'da yo'q. Kotlin ixchamroq: data class, xususiyatlar, standart va nomlangan argumentlar, when, kengaytma funksiyalar. Kotlin'da tekshiriladigan istisnolar (checked exceptions) yo'q. Funksiyalar birinchi darajali qiymat: lambda va yuqori tartibli funksiyalar tilning asosi, inline bilan ularning narxi yo'qotiladi. Asinxronlik uchun coroutines. Primitiv va obyekt turlari dasturchidan yashirin, kompilyator tanlaydi. == qiymatni solishtiradi. Kolleksiyalar faqat o'qish va o'zgartirish interfeyslariga bo'lingan.

Int va Int? farqi nima? Xotirada qanday saqlanadi?

Int null bo'la olmaydi va kompilyator uni iloji boricha primitiv int qiladi: 4 bayt. Int? null bo'lishi mumkin, primitivda esa null yo'q, shuning uchun u java.lang.Integer obyektiga qutilanadi: heap'da taxminan 16 bayt va unga havola. Generiklarda ham (List<Int>) qutilanadi. Ko'p sonli ro'yxatda bu xotira va tezlikka ta'sir qiladi, primitiv massiv kerak bo'lsa IntArray.

== va === farqi nima? val a: Int? = 1000; val b: Int? = 1000; a === b nima beradi?

== qiymatni solishtiradi (equals, null xavfsiz), === havolani, ya'ni bitta obyektmi. 1000 qutilanganda har safar yangi Integer obyekti yaratiladi, shuning uchun a === b yolg'on, a == b rost. 100 bo'lsa, ikkalasi ham rost, chunki JVM −128 dan 127 gacha Integer obyektlarini keshdan beradi. Kotlin qutilangan sonlar uchun === ishlatilsa ogohlantirish beradi, chunki natija qiymatga bog'liq.

val, const val va var farqi? lateinit va by lazy farqi?

var o'zgaradi, val bir marta tayinlanadi (lekin u ko'rsatgan obyekt o'zgarishi mumkin), const val kompilyatsiya paytida ma'lum oddiy qiymat va u ishlatilgan joyga qo'yib yuboriladi. lateinit: faqat var, null bo'lmaydigan, primitiv bo'lmagan tur, qiymat keyin beriladi, berilmasdan o'qilsa istisno. by lazy: faqat val, birinchi murojaatda hisoblanadi, sukut bo'yicha sinxronlashtirilgan, keyin keshlanadi.

data class nima yaratadi va qanday cheklovlari bor?

Asosiy konstruktordagi xususiyatlar asosida equals, hashCode, toString, copy va component1, component2 va hokazo (destrukturlash uchun). Klass tanasidagi xususiyatlar bularga kirmaydi. Cheklovlar: asosiy konstruktorda kamida bitta parametr, data class abstract, open, sealed yoki inner bo'la olmaydi. Java 16 dagi record bunga o'xshaydi, lekin copy yo'q va maydonlari doim o'zgarmas.

object va companion object nima? Ular Java'da nimaga aylanadi?

object yagona nusxali klass: kompilyator statik INSTANCE maydonini yaratadi, u klass birinchi yuklanganda bir marta va oqimlar uchun xavfsiz yaratiladi. companion object klass ichidagi shunday obyekt, nomi sukut bo'yicha Companion. Java'dan Klass.Companion.metod() deb chaqiriladi; to'g'ridan-to'g'ri statik metod bo'lishi uchun @JvmStatic qo'yiladi.

sealed class va enum farqi? Qachon qaysi biri?

enum: qat'iy qiymatlar ro'yxati, har biri bitta obyekt, hammasining tuzilishi bir xil (masalan, karta turi: UZCARD, HUMO, VISA). sealed: cheklangan variantlar, lekin har biri o'z maydonlariga ega alohida klass va har biridan ko'p nusxa (masalan, ekran holati yoki tarmoq natijasi: Success(data), Error(code, message), Loading). Ikkalasi ham when da to'liq tekshiriladi.

Kengaytma funksiya ichkarida nima? Uni ota klassda va bola klassda bir xil nom bilan yozsak nima bo'ladi?

Ichkarida bu statik metod, birinchi parametri o'sha obyekt. Klassning o'zi o'zgarmaydi va kengaytma private qismlarga kira olmaydi. Qaysi kengaytma chaqirilishi o'zgaruvchining e'lon qilingan turiga qarab kompilyatsiya paytida hal qilinadi, shuning uchun polimorfizm yo'q. Klassning o'z a'zo funksiyasi doim ustun.

Platforma turi nima va qanday xavfli?

Java'dan kelgan, null bo'lish-bo'lmasligi noma'lum tur, String!. Kompilyator uni tekshirmaydi, shuning uchun Java metodi null qaytarsa va biz uni String deb ishlatsak, NullPointerException. Himoya: qiymatni aniq tur bilan qabul qilish va Java kodida @Nullable annotatsiyalari.

Any, Unit va Nothing nima?

Any: barcha null bo'lmaydigan turlarning ildizi (Object ga o'xshash, equals, hashCode, toString). Unit: qaytaradigan qiymati yo'q funksiyaning turi, yagona qiymatli haqiqiy obyekt, shuning uchun generiklarda ishlatiladi (() -> Unit). Nothing: qiymati yo'q tur, hech qachon normal qaytmaydigan ifodalar uchun (throw, TODO()); u har qanday turning o'rnida tura oladi.

A2. Funksiyalar: lambda, inline, crossinline (7 ta savol)
inline funksiya nima va nima uchun kerak?

Kompilyator funksiyani chaqirish o'rniga uning tanasini va unga berilgan lambdalar tanasini chaqirilgan joyga ko'chiradi. Natijada lambda uchun obyekt yaratilmaydi va virtual chaqiruv yo'q, bu tez-tez chaqiriladigan yuqori tartibli funksiyalarda (map, filter, let) muhim. Qo'shimcha imkoniyatlar: lokal bo'lmagan return va reified tur parametrlari. Narxi: kod hajmi o'sadi, shuning uchun faqat kichik va lambda oladigan funksiyalar uchun.

noinline va crossinline farqi nima?

Ikkalasi ham inline funksiyaning lambda parametriga qo'yiladi. noinline: shu lambda umuman ko'chirilmaydi, oddiy obyekt bo'lib qoladi; kerak, agar lambdani o'zgaruvchida saqlash yoki inline bo'lmagan funksiyaga uzatish kerak bo'lsa. crossinline: lambda ko'chiriladi, lekin boshqa kontekstda bajariladi (boshqa lambda, Runnable, obyekt ichida), shuning uchun undan lokal bo'lmagan return taqiqlanadi. Qisqasi: noinline «ko'chirma», crossinline «ko'chir, lekin tashqi funksiyadan qaytishga ruxsat berma».

Lokal bo'lmagan return nima? Nega oddiy lambdada ruxsat yo'q?

inline funksiyaga berilgan lambda tanasi chaqirilgan joyga ko'chiriladi, shuning uchun undagi return tashqi funksiyadan chiqadi. Oddiy lambda esa obyekt, u istalgan vaqtda, hatto tashqi funksiya tugaganidan keyin chaqirilishi mumkin, u holda «tashqi funksiyadan qaytish»ning ma'nosi yo'q. Oddiy lambdadan faqat yorliqli return@yorliq bilan chiqiladi.

reified nima? Nega u faqat inline bilan ishlaydi?

JVM da generik turlar ish paytida o'chiriladi, funksiya ichida T ning klassi noma'lum. inline funksiya chaqirilgan joyga ko'chirilgani uchun u yerda tur aniq, va reified kompilyatorga T ni haqiqiy klass bilan almashtirishni aytadi. Shundan keyin T::class, is T, as T ishlaydi. Oddiy funksiya bitta nusxa bo'lib, hamma chaqiruvlar uchun umumiy, unda bunday almashtirishning iloji yo'q. Misol: Koin'dagi get<T>(), koinViewModel<T>().

let, run, with, apply, also farqi?

Ikki o'lchov. Obyekt blok ichida: it (let, also) yoki this (run, with, apply). Qaytaradi: blok natijasini (let, run, with) yoki obyektning o'zini (apply, also). Odatiy ishlatilishi: ?.let null bo'lmasa biror narsa qilish yoki aylantirish; apply obyektni sozlash (builder o'rnida); also yon ish, masalan log yozish; run obyekt ustida hisoblab natija olish; with bitta obyekt ustida bir nechta chaqiruv, kengaytma emas.

Lambda xotirada nima? Har safar yangi obyekt yaratiladimi?

Inline bo'lmagan joyda lambda FunctionN interfeysini amalga oshiradigan obyekt. Agar u tashqi o'zgaruvchilarni ushlasa, har chaqiruvda ular bilan yangi obyekt yaratiladi; ushlamasa, bitta umumiy nusxa ishlatiladi. Kotlin 2.0 dan boshlab JVM uchun lambdalar sukut bo'yicha invokedynamic orqali yaratiladi (Java 8 lambdalari kabi), oldin har biri alohida anonim klass edi; Android'da D8 buni yana klasslarga aylantiradi. Inline funksiyaga berilganda esa obyekt umuman yo'q.

Qachon inline qilmaslik kerak?

Funksiya katta bo'lsa yoki ko'p joyda chaqirilsa: kod hajmi o'sadi. Lambda parametri bo'lmasa: foydasi deyarli yo'q, kompilyator ogohlantiradi. Funksiya klassning private a'zolariga murojaat qilishi kerak bo'lsa: ochiq inline funksiya buni qila olmaydi. Rekursiv funksiyani inline qilib bo'lmaydi.

A3. Coroutines (9 ta savol)
Coroutine nima va u oqimdan nimasi bilan farq qiladi?

Coroutine to'xtatib turilishi va keyin davom ettirilishi mumkin bo'lgan hisoblash. U oqim emas: oqimlar ustida ishlaydi va kutish paytida oqimni bo'shatadi. Oqim operatsion tizim resursi, yuzlab kilobayt stek bilan, almashtirish qimmat; coroutine esa heap'dagi kichik obyekt, bir oqimda minglab bo'la oladi. Bekor qilish va xatolar tuzilmaviy parallellik orqali boshqariladi.

suspend funksiya ichkarida qanday ishlaydi?

Kompilyator har bir suspend funksiyaga yashirin Continuation parametrini qo'shadi va tanasini to'xtash nuqtalari bo'yicha holat mashinasiga aylantiradi (Continuation Passing Style). Lokal o'zgaruvchilar va label davom ettirish obyektida saqlanadi. To'xtaganda funksiya COROUTINE_SUSPENDED qaytaradi va oqim bo'shaydi. Natija tayyor bo'lganda resume chaqiriladi va funksiya label bo'yicha to'xtagan joyidan davom etadi.

Coroutine qanday turlari bor? launch va async farqi?

Builderlar: launch (Job qaytaradi, natijasiz, xato darhol ota-onaga), async (Deferred, natija await bilan, xato await da tashlanadi va ota-onani ham bekor qiladi), runBlocking (oqimni bloklaydi, faqat test va main uchun). Scope funksiyalari: coroutineScope, supervisorScope, withContext. Agar «turlar» deganda scope'lar so'ralsa: viewModelScope, lifecycleScope, o'z scope'imiz, GlobalScope (ishlatilmaydi).

Dispatchers qanday bo'ladi va qaysi biri qachon?

Main: asosiy oqim, UI uchun. IO: kutishga mo'ljallangan katta havza (64 tagacha oqim), tarmoq, fayl, baza. Default: yadrolar soniga teng oqimlar, protsessorni band qiladigan hisob uchun. Unconfined: maxsus holatlar. Oqim almashtirish withContext bilan. Repozitoriy funksiyalari main-safe bo'lishi kerak: dispetcherni o'zi tanlaydi.

Coroutine qanday bekor qilinadi?

job.cancel() yoki scope'ni bekor qilish bilan. Bekor qilish hamkorlikda: coroutine buni keyingi to'xtash nuqtasida sezadi va CancellationException tashlanadi, finally bajariladi. Uzoq hisobda ensureActive(), isActive yoki yield() bilan tekshirish kerak. CancellationException ni yutib yubormaslik kerak. Bekor qilingandan keyin finally da suspend chaqiruv kerak bo'lsa, withContext(NonCancellable).

Job va SupervisorJob farqi? viewModelScope qanday tuzilgan?

Oddiy Job'da bolaning xatosi ota-onani bekor qiladi, u esa qolgan bolalarni. SupervisorJob'da bolaning xatosi tarqalmaydi, faqat o'sha bola tugaydi. viewModelScope = SupervisorJob() + Dispatchers.Main.immediate, va ViewModel tozalanganda bekor qilinadi.

Coroutine'da xatoni qanday ushlash kerak?

Kutilgan xatolarni so'rov joyida try/catch bilan (faqat kerakli turlar, CancellationException ni qayta tashlab). Natijani Result yoki sealed natija turiga aylantirib ViewModel'ga berish. Kutilmagan xatolar uchun ildiz coroutine'da CoroutineExceptionHandler: u faqat ildizda yoki supervisor bolasida ishlaydi. Parallel so'rovlarda chegarani coroutineScope yoki supervisorScope bilan qo'yish.

withContext va launch(Dispatchers.IO) farqi?

withContext yangi coroutine yaratmaydi: joriy coroutine'ni boshqa dispetcherga o'tkazadi, blok tugaguncha kutadi va natijani qaytaradi, ya'ni ketma-ket. launch(Dispatchers.IO) yangi bola coroutine boshlaydi va darhol qaytadi, natija yo'q, ya'ni parallel. Natija kerak bo'lgan oqim almashtirish uchun withContext.

Coroutine'larni qanday test qilasiz?

kotlinx-coroutines-test: runTest virtual vaqt bilan ishlaydi (delay darhol o'tadi), StandardTestDispatcher va UnconfinedTestDispatcher, Dispatchers.setMain bilan asosiy dispetcherni almashtirish. Dispetcherlarni DI orqali berish ularni testda almashtirishni osonlashtiradi.

A4. Flow: StateFlow va SharedFlow (8 ta savol)
Flow nima va suspend funksiyadan nimasi bilan farq qiladi?

Suspend funksiya bitta qiymat qaytaradi, Flow vaqt davomida ko'p qiymat chiqaradi. Flow sovuq: collect chaqirilgunga qadar hech narsa bajarilmaydi va har bir kollektor uchun qaytadan ishga tushadi. Coroutines ustiga qurilgan, shuning uchun bekor qilish va dispetcherlar xuddi coroutine'lardagidek ishlaydi.

Sovuq va issiq oqim farqi?

Sovuq oqim har bir kuzatuvchi uchun alohida ishga tushadi va kuzatuvchi bo'lmasa ishlamaydi (flow { }). Issiq oqim kuzatuvchilardan mustaqil yashaydi va qiymatlarni hammaga tarqatadi (StateFlow, SharedFlow). Sovuqni issiqqa stateIn/shareIn aylantiradi.

StateFlow va SharedFlow farqi? LiveData'dan farqi?

StateFlow: boshlang'ich qiymat shart, doim joriy qiymat bor, yangi kuzatuvchi uni darhol oladi, teng qiymatni qayta yubormaydi, sekin kuzatuvchiga oxirgisini beradi. SharedFlow: boshlang'ich qiymat yo'q, replay va bufer sozlanadi, teng qiymatlar ham yuboriladi: hodisalar uchun. LiveData'dan farqi: platformadan mustaqil (domain qavatida ham ishlaydi), operatorlarga boy, istalgan dispetcherda; lekin hayot siklini o'zi bilmaydi, shuning uchun repeatOnLifecycle yoki collectAsStateWithLifecycle bilan kuzatiladi.

Bir martalik hodisalarni (navigatsiya, Snackbar) qanday yuborasiz?

Uchta yondashuv: Channel va receiveAsFlow (har bir hodisa bir marta, bitta kuzatuvchiga, bufer tufayli aylantirishda yo'qolmaydi); SharedFlow (replay 0 bo'lsa kuzatuvchi yo'q paytda yo'qoladi); hodisani holatning bir qismi qilish va ekran uni iste'mol qilgach ViewModel'ga xabar berish (Google tavsiyasi, eng ishonchli). Men odatda ... (o'zingiz tanlagan va DigitalBank'da ishlatganingizni ayting, savdosini tushuntiring).

stateIn dagi WhileSubscribed(5000) nimani bildiradi?

Yuqoridagi sovuq oqim faqat kuzatuvchi bor paytda ishlaydi; oxirgi kuzatuvchi ketgach 5 sekund kutib, keyin to'xtaydi. 5 sekund ekran aylantirilganda oqimni qayta boshlamaslik uchun yetarli, ilova fonga o'tganda esa resurslarni bo'shatadi. Holat esa saqlanib qoladi va qaytganda kuzatuvchi oxirgi qiymatni darhol oladi.

flatMapLatest, flatMapConcat va flatMapMerge farqi?

Uchalasi ham har bir qiymat uchun yangi oqim ochadi. flatMapLatest: yangi qiymat kelsa eski ichki oqimni bekor qiladi (qidiruv). flatMapConcat: ichki oqimlarni navbat bilan, biri tugagach keyingisi. flatMapMerge: parallel, natijalar aralash keladi.

flowOn nima qiladi? Nega collect ichida withContext qilib bo'lmaydi?

flowOn undan yuqoridagi operatorlar va emitter qaysi dispetcherda ishlashini o'zgartiradi, kollektor o'z kontekstida qoladi. Flow «kontekstni saqlash» qoidasiga amal qiladi: emit kollektorning kontekstida chaqirilishi shart, shuning uchun flow { withContext(IO) { emit(x) } } xato beradi. To'g'risi flowOn(Dispatchers.IO).

Flow'ni qanday test qilasiz?

runTest ichida flow.toList() yoki first(); issiq oqimlar uchun Turbine kutubxonasi: flow.test { assertEquals(a, awaitItem()) }. StateFlow da boshlang'ich qiymatni hisobga olish kerak.

A5. Arxitektura: Clean, SOLID, MVI (7 ta savol)
Clean Architecture qavatlarini tushuntiring. Kim kimni biladi?

Presentation (Compose ekranlar, ViewModel), domain (use case'lar, biznes modellari, repozitoriy interfeyslari, sof Kotlin) va data (repozitoriy amalga oshirilishi, Retrofit, Room, DTO va mapper'lar). Bog'liqlik faqat domain tomonga: presentation va data domain'ni biladi, domain hech kimni bilmaydi. Data'ning domain'ga bog'liqligi interfeys orqali: bog'liqlikni teskari aylantirish. Ularni ishga tushishda DI ulaydi.

Use case nima uchun kerak? Har doim kerakmi?

Bitta biznes amalini (limit tekshirish, komissiya hisoblash, bir nechta repozitoriyni birlashtirish) bir joyda saqlash, qayta ishlatish va Android'siz testlash uchun. Har doim emas: faqat repozitoriyni chaqiradigan use case qo'shimcha qatlam xolos. Google qo'llanmasida domain qavati ixtiyoriy.

Nega DTO, Entity va domain modeli alohida?

Har biri o'z sababga ko'ra o'zgaradi: server formati, baza sxemasi, biznes qoidasi. Alohida bo'lsa, biri o'zgarganda faqat mapper o'zgaradi. DTO da hamma maydon ixtiyoriy va server nomlari bilan, domain modelida majburiy va to'g'ri turlar bilan: xato chegarada, mapper'da ushlanadi.

SOLID ni misollar bilan ayting.

S: bir klass bitta sababga ko'ra o'zgaradi (ViewModel tarmoq so'rovini o'zi yozmaydi). O: yangi to'lov turi qo'shish mavjud kodni o'zgartirmasdan, yangi klass qo'shish bilan (interfeys va ro'yxat, when zanjiri emas). L: voris otaning va'dalarini buzmaydi (fake repozitoriy haqiqiysi o'rnida bemalol ishlaydi). I: katta interfeys o'rniga kichiklari (kartani faqat o'qiydigan ekranga yozish metodlari berilmaydi). D: ViewModel aniq klassga emas, interfeysga bog'liq va u tashqaridan beriladi.

MVVM va MVI farqi? Nega MVI?

MVVM'da bir nechta mustaqil kuzatiladigan maydon va bir nechta metod; MVI'da bitta o'zgarmas holat, bitta niyatlar kirishi, holat faqat reduktorda o'zgaradi, bir martalik ishlar effekt kanalida. MVI'da holat doim izchil (yuklanmoqda va xato bir vaqtda bo'lmaydi), testlash oson (niyat berdik, holatni tekshirdik), holatlar ketma-ketligini log qilish mumkin. Narxi: ko'proq kod va har safar holat nusxasi.

Loyihangiz arxitekturasini chizib bering.

Bu yerda o'z loyihangizni ayting: modullar (feature va core), har bir ekranda Compose ekran, ViewModel (StateFlow holat, niyatlar), use case'lar qayerda bor, repozitoriy (tarmoq va kesh), Retrofit, Room, DI (qaysi biri), navigatsiya. DigitalBank'da kredit, depozit va kartalar bo'limlarini siz qurgansiz: bitta ekranni misol qilib, ma'lumot serverdan ekrangacha qanday yetib kelishini qadam-baqadam ayting.

ViewModel ekran aylantirilganda qanday saqlanadi? Jarayon o'limida-chi?

ViewModel ViewModelStore da saqlanadi, u esa konfiguratsiya o'zgarishida yangi Activity'ga o'tkaziladi. Activity butunlay tugaganda (orqaga bosish) onCleared chaqiriladi. Jarayon o'limida ViewModel yo'qoladi; kichik holat SavedStateHandle orqali Bundle ga saqlanadi va qaytariladi.

A6. Dependency Injection: Hilt va Koin (8 ta savol)
DI nima va nima uchun kerak?

Klass bog'liqliklarini o'zi yaratmasdan konstruktor orqali olishi. Natijada klasslar bir-biridan ajraladi (interfeysga bog'lanadi), testda soxtasini berish oson, obyektlarning yashash muddati (singleton, ekran bo'yicha) bir joyda boshqariladi, va yaratish kodi takrorlanmaydi. DI konteyner esa graf bo'yicha obyektlarni avtomatik yig'adi.

DI va Service Locator farqi? Koin qaysi biri?

DI'da bog'liqliklar tashqaridan beriladi va konstruktorda ko'rinadi; Service Locator'da klass ularni o'zi ro'yxatdan so'raydi, bog'liqliklar yashirin. Koin ichkarida lokator: ish paytida tur bo'yicha jadvaldan topadi. Lekin modullarda konstruktor orqali e'lon qilinsa (singleOf(::Repo)), klasslarimiz uchun bu DI: ular Koin'ni bilmaydi. by inject() faqat Activity kabi chegaralarda.

Koin va Hilt farqi? Nega loyihangizda Koin?

Hilt (Dagger) grafni kompilyatsiyada tekshiradi va kod yaratadi: xatolar yig'ishda, ish paytida narxi yo'q, lekin yig'ish sekinroq va o'rganish qiyinroq. Koin oddiy Kotlin DSL, kod yaratmaydi, graf ish paytida yig'iladi: yig'ish tez, oson, Multiplatform'da ishlaydi, lekin bog'lanmagan bog'liqlik ish paytida chiqadi; bu verify testi yoki annotatsiyalar bilan yopiladi. Tanlov jamoa hajmi va loyiha talablariga bog'liq.

Koin ichkarida qanday ishlaydi?

startKoin modullardagi e'lonlarni tur (va nom) bo'yicha kalit bilan ro'yxatga yozadi. get<T>() chaqirilganda T bo'yicha e'lonni topadi, lambdasini chaqiradi; lambda ichidagi get() lar zanjir bo'yicha qolganlarini topadi. single natijasi saqlanadi, factory har safar qayta. get<T>() inline va reified bo'lgani uchun T ning klassini biladi (A2-dars).

single, factory va viewModel farqi?

single: ilova bo'yicha bitta nusxa (OkHttp, Retrofit, baza, repozitoriy). factory: har so'ralganda yangi (use case, formatter). viewModel: Jetpack ViewModelStore orqali, ekran bilan yashaydi va aylantirishdan omon qoladi, onCleared da tozalanadi.

Interfeys va uning amalga oshirilishini qanday bog'laysiz?

Koin: single<CardRepository> { CardRepositoryImpl(get(), get()) } yoki singleOf(::CardRepositoryImpl) { bind<CardRepository>() }. Hilt: abstrakt modulda @Binds abstract fun bind(impl: CardRepositoryImpl): CardRepository, Impl'da @Inject constructor.

Hilt komponentlari va scope'lari?

SingletonComponent (@Singleton, ilova), ActivityRetainedComponent (@ActivityRetainedScoped, aylantirishdan omon qoladi), ViewModelComponent (@ViewModelScoped), ActivityComponent, FragmentComponent, ViewComponent. Pastki komponent yuqoridagilarning obyektlarini ko'radi, aksincha emas.

DI bilan qanday test yozasiz?

Asosiy usul: ViewModel va repozitoriyni konteynersiz, konstruktoriga soxta yoki mock bog'liqlik berib testlash. Integratsiya testlarida Koin'da test moduli bilan almashtirish, Hilt'da @TestInstallIn yoki @UninstallModules. Koin modullari uchun verify() testi.

A7. Jetpack Compose (8 ta savol)
Rekompozitsiya nima va Compose nimani qayta chizishni qanday biladi?

Rekompozitsiya: o'qilgan holat o'zgarganda tegishli composable funksiyalarni yangi qiymatlar bilan qayta chaqirish. Compose kompozitsiya paytida har bir funksiya qaysi State obyektlarini o'qiganini snapshot tizimi orqali yozib oladi. State o'zgarganda faqat uni o'qigan scope'lar yaroqsiz deb belgilanadi va keyingi kadrda qayta bajariladi. Bolalar parametrlari o'zgarmagan bo'lsa o'tkazib yuboriladi.

Barqarorlik nima? Kuchli o'tkazib yuborish rejimi nimani o'zgartirdi?

Barqaror tur: Compose uning o'zgarganini ishonchli biladi (o'zgarmas, yoki o'zgarishi kuzatiladigan). Eski rejimda beqaror parametrli (masalan List) composable hech qachon o'tkazib yuborilmasdi. Kotlin 2.0.20 dan sukut bo'yicha yoqilgan kuchli o'tkazib yuborish rejimida hamma qayta ishga tushadigan composable o'tkazib yuboriladigan: beqaror parametrlar ===, barqarorlar equals bilan solishtiriladi, composable ichidagi lambdalar avtomatik remember qilinadi. Shuning uchun holatni o'zgarmas tutish (yangi ro'yxat, copy) yana ham muhim.

remember va rememberSaveable farqi?

remember qiymatni rekompozitsiyalar orasida saqlaydi, lekin konfiguratsiya o'zgarishi va jarayon o'limida yo'qoladi. rememberSaveable Bundle orqali saqlaydi va ulardan omon qoladi; faqat Bundle'ga sig'adigan turlar yoki Saver bilan. Asosiy ekran holati baribir ViewModel'da (SavedStateHandle bilan); rememberSaveable UI elementining kichik holati uchun: matn maydoni, ochiq-yopiq bo'lim.

State hoisting nima va nega kerak?

Holatni composable ichida saqlamasdan, uni parametr qilib olish va o'zgarishni lambda bilan yuqoriga berish. Natijada composable holatsiz: qayta ishlatiladi, preview va testda oson, va holat bitta manbada (single source of truth). Qiymat pastga, hodisa yuqoriga: bu UDF ning ekran ichidagi ko'rinishi.

Qanday yon ta'sir API larini bilasiz? LaunchedEffect qachon qayta ishga tushadi?

LaunchedEffect (coroutine, kirishda boshlanadi, kalit o'zgarsa qayta, chiqishda bekor), DisposableEffect (tinglovchi, onDispose bilan tozalash), rememberCoroutineScope (hodisadan coroutine boshlash), SideEffect (har rekompozitsiyadan keyin), rememberUpdatedState (effektni qayta boshlamasdan oxirgi qiymat), produceState, derivedStateOf, snapshotFlow (State ni Flow ga). LaunchedEffect faqat kalitlaridan biri o'zgarganda qayta ishga tushadi.

LazyColumn da key nima uchun?

Elementni ro'yxatdagi o'rni bo'yicha emas, identifikatori bo'yicha tanish uchun. Kalit bo'lsa, element qo'shilganda yoki o'chirilganda qolganlari qayta chizilmaydi, element ichidagi remember holati o'z elementida qoladi va animatsiyalar to'g'ri ishlaydi.

Compose ekranini qanday tezlashtirasiz?

O'lchashdan boshlash (Layout Inspector'dagi rekompozitsiya hisoblagichlari, Macrobenchmark, release yig'masida tekshirish). Keyin: o'zgarmas holat va barqaror turlar, ro'yxatlarda key va contentType, og'ir hisobni composition'dan chiqarish (ViewModel yoki remember), tez o'zgaradigan holatni lambda modifierlarda o'qish, derivedStateOf. Baseline Profiles ishga tushish va birinchi chizishni tezlashtiradi.

Compose va View tizimini birga ishlatish mumkinmi?

Ha: View ichida ComposeView, Compose ichida AndroidView (masalan xarita yoki eski maxsus komponent). Katta loyihalar ekranma-ekran ko'chiriladi.

A8. Navigatsiya: Compose Navigation va Navigation 3 (6 ta savol)
Compose'da navigatsiya qanday tashkil qilinadi?

Navigation Compose: NavHost va NavController, 2.8 dan tur xavfsiz @Serializable marshrutlar, composable<T>, argumentlar toRoute va SavedStateHandle orqali, ichki graflar, chuqur havolalar. Yangi yondashuv Navigation 3: stek ilovaning o'z holati (rememberNavBackStack), NavDisplay uni kuzatadi, entryProvider kalitni ekranga aylantiradi.

Navigation 3 nima uchun yaratilgan? Navigation 2 dan farqi?

Navigation 2 da stek NavController ichida yashirin, Compose holatiga mos emas edi; argumentlar uchun satr marshrutlar; moslashuvchan (ro'yxat va tafsilot yonma-yon) layoutlar qiyin. Navigation 3 da stek oddiy kuzatiladigan ro'yxat, uni o'zingiz o'zgartirasiz; kalitlar tur xavfsiz obyektlar; dekoratorlar bilan holat va ViewModel saqlanadi; sahnalar bilan bir vaqtda bir nechta ekran. Kutubxona kichik, almashtiriladigan qismlardan iborat. 1.0 barqaror versiyasi 2025-yil noyabrda chiqdi.

Ekranga argument qanday beriladi? ViewModel uni qanday oladi?

Navigation 2: marshrut klassining maydoni, ViewModel'da savedStateHandle.toRoute<KartaDetail>(). Navigation 3: kalitning maydoni, entry<KartaDetail> { key -> } ichida olinadi va ViewModel'ga parametr qilib beriladi (DI'da parametr sifatida: Koin'da parametersOf(key.id)). Faqat identifikator, katta obyekt emas.

Kirishdan keyin «orqaga» PIN ekraniga qaytarmasligi uchun nima qilasiz?

Navigation 2: navigate(Asosiy) { popUpTo(KirishGraf) { inclusive = true } }. Navigation 3: stekni tozalab, faqat asosiy ekranni qo'shish. Sessiya tugaganda ham shunday: stek tozalanib, kirish ekrani qo'yiladi.

ViewModel qaysi ekranga bog'lanadi va qachon tozalanadi?

Navigation 2: har bir NavBackStackEntry ViewModelStoreOwner; ekran stekda ekan ViewModel yashaydi, olib tashlanganda tozalanadi. Graf darajasida umumiy ViewModel uchun graf yozuvi owner sifatida beriladi. Navigation 3: rememberViewModelStoreNavEntryDecorator har bir yozuvga ViewModelStore beradi, kalit stekdan olib tashlanganda u tozalanadi.

Bir martalik navigatsiya hodisasini ViewModel'dan qanday yuborasiz?

ViewModel Channel orqali effekt yuboradi (yoki holatda belgi va «bajarildi» niyati), ekran uni LaunchedEffect ichida kuzatib, navigatsiyani bajaradi. ViewModel NavController'ni bilmaydi.

A9. Tarmoq: Retrofit, Ktor, tokenlar (8 ta savol)
Retrofit ichkarida qanday ishlaydi?

retrofit.create() Java dinamik proksi bilan interfeysni amalga oshiradi. Metod chaqirilganda annotatsiyalar (bir marta tahlil qilinib keshlanadi) bo'yicha OkHttp Request yig'iladi, Call bajariladi (suspend bo'lsa coroutine to'xtatiladi), javob konvertor orqali obyektga aylantiriladi. Tarmoq ishini OkHttp qiladi: ulanishlar havzasi, interceptor zanjiri, TLS, kesh.

Interceptor va Authenticator farqi? Application va network interceptor farqi?

Interceptor har bir so'rov va javobga ta'sir qiladi (sarlavha, log). Authenticator faqat 401 javobida chaqiriladi va yangi so'rov qaytaradi (yoki null: taslim). Application interceptor bitta chaqiruvga bir marta ishlaydi, qayta yo'naltirish va qayta urinishlarni ko'rmaydi; network interceptor har bir haqiqiy tarmoq almashinuviga, va haqiqiy ulanishni ko'radi.

Token muddati tugaganda nima bo'ladi? Bir vaqtda bir nechta so'rov 401 olsa-chi?

Server 401 qaytaradi, Authenticator refresh token bilan yangi access token oladi, saqlaydi va so'rovni yangi token bilan takrorlaydi. Refresh ham muvaffaqiyatsiz bo'lsa, sessiya tugaydi: tokenlar o'chiriladi va foydalanuvchi kirish ekraniga yuboriladi. Bir vaqtdagi 401 larda yangilash qulf ostida: birinchisi yangilaydi, qolganlari kutadi va token allaqachon yangilanganini ko'rib, yangilamasdan takrorlaydi.

Tarmoq xatolarini qanday qayta ishlaysiz?

Repozitoriyda texnik istisnolarni turlayman: IOException (internet yo'q yoki uzildi), SocketTimeoutException, HttpException kod bo'yicha (401, 403, 404, 409, 429, 5xx), serializatsiya xatosi, va tanadagi biznes xatosi. Ularni domain'ning sealed xato turiga aylantirib, Result bilan qaytaraman. ViewModel holatga xatoni qo'yadi, ekran turga qarab xabar va «qayta urinish» tugmasini ko'rsatadi. CancellationException qayta tashlanadi.

Gson, Moshi va kotlinx.serialization farqi?

Gson refleksiya bilan ishlaydi va Kotlin konstruktorini chetlab o'tadi: null bo'lmaydigan maydonga null tushishi va standart qiymatlar ishlamasligi mumkin. Moshi Kotlin uchun kod yaratish rejimiga ega. kotlinx.serialization kompilyator plagini bilan serializatorlarni kompilyatsiyada yaratadi, refleksiyasiz, Multiplatform, Kotlin turlarini to'liq hurmat qiladi. Yangi loyihada kotlinx.serialization.

Retrofit va Ktor farqi? Qachon qaysi biri?

Retrofit annotatsiyali interfeys, OkHttp ustida, JVM/Android uchun, eng keng tarqalgan, interceptor va Authenticator bilan kengaytiriladi. Ktor Kotlin DSL, Multiplatform, dvigatellar va plaginlar (Auth plagini token yangilashni o'zi boshqaradi). Faqat Android bo'lsa ikkalasi ham yaxshi; iOS bilan umumiy kod kerak bo'lsa Ktor.

JWT nima? Uning ichida parol saqlash mumkinmi?

Uch qism: sarlavha (algoritm), ma'lumot (foydalanuvchi, muddat, ruxsatlar), imzo; base64url bilan kodlangan va nuqta bilan ajratilgan. U imzolangan, shifrlanmagan: ichini har kim o'qiy oladi, lekin o'zgartirsa imzo buziladi. Shuning uchun ichida maxfiy ma'lumot yo'q. Mijoz tomonda muddatni o'qib, so'rovdan oldin yangilash mumkin, lekin tekshiruvni server qiladi.

Nega to'lov so'rovini avtomatik qayta yuborib bo'lmaydi?

Javob kelmagani so'rov bajarilmaganini bildirmaydi: server bajargan bo'lishi mumkin. Qayta yuborish ikkinchi to'lov. Yechim: idempotentlik kaliti sarlavhasi va server tomonda takroriy kalitni aniqlash, yoki operatsiya holatini alohida tekshirish.

A10. Lokal saqlash: Room va DataStore (7 ta savol)
Room nima va SQLiteOpenHelper'dan nimasi yaxshi?

SQLite ustidagi abstraksiya: Entity, DAO, Database. SQL kompilyatsiyada tekshiriladi, mapping kodi yaratiladi, suspend va Flow qo'llab-quvvatlanadi, asosiy oqimda so'rovga sukut bo'yicha ruxsat bermaydi, migratsiya va sxema eksporti bor, InvalidationTracker orqali o'zgarishlarni xabar qiladi.

Room Flow qanday qilib yangi ma'lumotni chiqaradi?

InvalidationTracker SQLite triggerlari bilan o'zgargan jadvallarni belgilaydi. Yozuvchi tranzaksiya tugagach, shu jadvallarni o'qiydigan Flow lar so'rovni qayta bajaradi va yangi natijani chiqaradi. Kuzatuv jadval darajasida, shuning uchun natija o'zgarmagan bo'lsa ham chiqishi mumkin: distinctUntilChanged.

Migratsiya nima? U bo'lmasa nima bo'ladi?

Versiya oshganda eski bazani ma'lumotini saqlab yangi sxemaga o'tkazish: qo'lda Migration(from, to) SQL bilan yoki AutoMigration eksport qilingan sxemalar asosida. Migratsiya topilmasa, Room IllegalStateException bilan qulaydi; fallbackToDestructiveMigration bazani o'chiradi va ma'lumot yo'qoladi. MigrationTestHelper bilan testlanadi.

Oflayn rejimni qanday qilasiz?

Bitta haqiqat manbai: ekran faqat Room Flow ni kuzatadi; repozitoriy tarmoqdan yangilaganda bazaga yozadi. Internet yo'q bo'lsa, ekranda oxirgi kesh va «yangilanmadi» belgisi. Yozish amallari (masalan qoralama) navbatga qo'yilib, WorkManager bilan tarmoq paydo bo'lganda yuboriladi. Pul o'tkazmasini oflayn navbatga qo'yish esa xavfli va odatda qilinmaydi.

DataStore va SharedPreferences farqi? Preferences va Proto farqi?

DataStore asinxron (Flow, suspend), asosiy oqimni bloklamaydi, tranzaksiyali, xatolarni ochiq beradi, tur xavfsiz kalitlar. SharedPreferences sinxron o'qiydi, apply ANR ga olib kelishi mumkin, tranzaksiya yo'q. Preferences DataStore: turlangan kalit-qiymat. Proto DataStore: butun sozlamalar bitta turlangan obyekt, protobuf yoki kotlinx.serialization bilan.

Tokenni qayerda saqlaysiz?

Shifrsiz SharedPreferences yoki DataStore'da emas. Refresh token Android Keystore'dagi kalit bilan shifrlanib (Tink bilan, DataStore yoki faylda) saqlanadi; EncryptedSharedPreferences endi eskirgan deb belgilangan. Access token iloji boricha faqat xotirada. Batafsil A12 da.

Room 3.0 haqida eshitganmisiz?

2026-yil martida birinchi alfa chiqdi: faqat KSP va faqat Kotlin, DAO metodlari suspend yoki Flow bo'lishi shart (bloklovchi metodlar yo'q), to'liq SQLiteDriver API ustida (Multiplatform, veb ham), paket nomi androidx.room3 ga o'zgaradi. Room 2.x texnik qo'llab-quvvatlash rejimida. (Holatini suhbatdan oldin tekshiring.)

A11. Firebase va Git (7 ta savol)
Push xabar qanday ishlaydi, boshidan oxirigacha?

Ilova FCM SDK dan ro'yxatdan o'tish tokenini oladi va backendga yuboradi (va onNewToken da yangilaydi). Backend FCM HTTP v1 API ga service account OAuth2 tokeni bilan xabar yuboradi. FCM uni Google Play xizmatlarining doimiy ulanishi orqali qurilmaga yetkazadi. Notification xabar fonda tizim tomonidan ko'rsatiladi, data xabar esa doim FirebaseMessagingService.onMessageReceived ga keladi. Ko'rsatish uchun Android 13 dan ruxsat va kanal kerak.

Notification va data xabar farqi?

Notification xabar: fonda tizim o'zi ko'rsatadi, ilova kodi chaqirilmaydi, bosilganda data extras bilan ilova ochiladi; oldinda onMessageReceived. Data xabar: doim onMessageReceived, ko'rsatishni ilova o'zi qiladi. Ikkalasini birga yuborsa, fonda notification kabi ishlaydi.

FCM tokeni qachon o'zgaradi va nima qilish kerak?

Ilova qayta o'rnatilganda, ma'lumotlari tozalanganda, yangi qurilmaga tiklanganda, yoki FCM uni yangilaganda. onNewToken da yangi tokenni backendga yuborish, chiqishda esa backenddan o'chirish (boshqa foydalanuvchiga eski egasining pushlari kelmasligi uchun).

Crashlytics'da obfuskatsiya qilingan stek izini qanday o'qiysiz?

R8 yig'ishda mapping.txt yaratadi; Crashlytics Gradle plagini uni release yig'masi bilan yuklaydi, konsol stekni asl nomlarga qaytaradi. Yuklanmagan bo'lsa, shu yig'maning mapping faylini qo'lda yuklash mumkin. Qo'shimcha kontekst uchun custom key va loglar, ushlangan muhim xatolar uchun recordException.

Analytics'da qanday hodisalarni yozasiz?

Biznes uchun muhim voronkalar: kirish, karta qo'shish, o'tkazma boshlash, tasdiqlash, muvaffaqiyat yoki xato turi. Parametrlarda faqat toifalar va oraliqlar, shaxsiy ma'lumot yo'q. Nomlash kelishuvi va hodisalar ro'yxati hujjatlashtiriladi; ishlab chiqishda DebugView bilan tekshiriladi.

GitFlow'ni tushuntiring. Hotfix qanday qilinadi?

main (relizlar va teglar), develop (integratsiya), feature/* (develop dan, PR bilan develop ga), release/* (develop dan, faqat tuzatishlar, main va develop ga), hotfix/* (main dan, tuzatish, main ga yangi teg bilan va develop ga). Hotfix: main dan tarmoq, tuzatish va test, versiyani oshirish (patch), PR, main ga birlashtirish, teg, develop ga birlashtirish, do'konga yig'ma.

Kod ko'rib chiqishda nimalarga qaraysiz?

To'g'riligi va chekka holatlar; arxitektura qoidalari (qavatlar, ViewModel'da Context yo'q); coroutine va hayot sikli xatolari; xavfsizlik (log'da token, ochiq ma'lumot); unumdorlik (Compose'da keraksiz rekompozitsiya, asosiy oqimda ish); testlar; nomlar va o'qilishi. Sharh aniq va asoslangan, taklif bilan.

A12. Mobil bank xavfsizligi (7 ta savol)
Tokenni qurilmada qanday xavfsiz saqlaysiz?

Access token qisqa muddatli, iloji boricha xotirada. Refresh token shifrlangan: Tink AEAD bilan, Tink kalitlari Android Keystore'dagi asosiy kalit bilan himoyalangan, natija DataStore'da yoki faylda. EncryptedSharedPreferences eskirgan deb belgilangan, uning o'rnida DataStore va Tink. Kerak bo'lsa refresh tokenni ochish biometriyaga bog'lanadi (CryptoObject). Tokenlar zaxira nusxadan chiqariladi, chiqishda o'chiriladi.

Sertifikat pinning nima va qanday qilinadi? Kamchiligi?

Ilova faqat ma'lum ochiq kalitli sertifikatga ishonadi: hujumchi o'z CA sini qurilmaga qo'shgan bo'lsa ham MITM ishlamaydi. OkHttp CertificatePinner yoki Network Security Config pin-set. Kamchiligi: server kaliti almashganda ilova ishlamay qoladi, shuning uchun zaxira pin, muddat va almashtirish rejasi kerak.

Android 7 dan tarmoq xavfsizligida nima o'zgardi?

Ilovalar sukut bo'yicha foydalanuvchi o'rnatgan CA larga ishonmaydi, faqat tizimnikiga; bu Network Security Config bilan sozlanadi. Android 9 dan shifrsiz HTTP sukut bo'yicha taqiqlangan.

Biometrik autentifikatsiyani qanday to'g'ri qilasiz?

BiometricPrompt va CryptoObject: Keystore'da faqat biometriyadan keyin ishlatiladigan kalit (setUserAuthenticationRequired), yangi barmoq izi qo'shilganda bekor bo'ladigan. Muvaffaqiyatli biometriyadan keyingina shu kalit bilan tokenni ochish yoki imzolash mumkin. Shunchaki «muvaffaqiyat» qayta chaqiruviga ishonish root qurilmada chetlab o'tilishi mumkin. Zaxira usul PIN.

Root qilingan qurilmani qanday aniqlaysiz va nima qilasiz?

Asosiy vosita Play Integrity API: xulosa serverda tekshiriladi. Qo'shimcha mahalliy tekshiruvlar (su, ma'lum ilovalar, tizim xususiyatlari) chetlab o'tilishi mumkinligini hisobga olaman. Reaksiya biznes bilan kelishiladi: ogohlantirish, ba'zi amallarni cheklash yoki qo'shimcha tasdiqlash. SafetyNet Attestation 2025-yil yanvarida o'chirilgan.

Bank ilovasi uchun yana qanday xavfsizlik choralarini bilasiz?

FLAG_SECURE maxfiy ekranlarda; release'da log yo'q; R8; exported komponentlar faqat zarur bo'lsa; chuqur havola ma'lumotlarini tekshirish; WebView'da faqat ishonchli domen va JS interfeysni cheklash; bufer uchun maxfiy belgi; zaxira nusxadan chiqarish; sessiya muddati va fonda qolganda qayta PIN; overlay himoyasi; ilovada sir saqlamaslik; muhim tekshiruvlar serverda; OWASP MASVS bo'yicha audit.

Ilovada API kalitini qanday yashirasiz?

Yashirib bo'lmaydi: ilovaga qo'yilgan har qanday sir oxir-oqibat topiladi (obfuskatsiya, NDK va shifrlash faqat vaqtni cho'zadi). To'g'ri yechim: maxfiy kalit serverda, ilova foydalanuvchi sessiyasi bilan o'z serverimizga murojaat qiladi. Ilovadagi ochiq kalitlar (masalan, xarita kaliti) paket nomi va imzo bilan cheklanadi.

Mustahkamlash testi

120 ta savol, har bir darsdan 10 tadan 10 tagacha. Har javobdan keyin izoh va darsga havola chiqadi. Savollar va variantlar har safar aralashtiriladi. Bitta dars bo'yicha alohida ishlash ham mumkin; oxirida darslar bo'yicha natija jadvali va faqat xatolarni qayta ishlash tugmasi.

Suhbat mashqi

Bilim bor, lekin suhbatda uni ishonchli gapirib berish alohida ko'nikma. O'tgan suhbatda savollarning ko'pi nazariyadan edi va asosiy e'tiroz Android'dan uzoqroq tanaffus bo'ldi. Quyidagilar shu ikkalasiga qaratilgan.

1O'zingizni tanishtirish (60–90 soniya)

Tuzilish: kim, nima qilgan, nimani yaxshi biladi, nega aynan shu vakansiya. Quyidagi namunani o'z so'zlaringiz bilan moslang va ovoz chiqarib, soat bilan bir necha marta ayting.

«Men Sadullaman, Fido-Biznes kompaniyasida olti yildan beri ishlayman. Android dasturchi bo'lib boshlaganman: uch yil to'liq Android'da, Universal Bank uchun DigitalBank ilovasida kreditlar, depozitlar va kartalar ro'yxati bo'limlarini qilganman, MVVM arxitekturasida. Keyin backend'ga ham o'tdim: Java, Spring Boot, Oracle PL/SQL, yuridik shaxslar uchun internet-banking (КИБ) tizimlari va to'lov integratsiyalari: Uzcard, Humo, Payme, Click.

Shuning uchun B2B DBO ni ikki tomondan bilaman: ilova tomonini ham, uning orqasidagi bank backend'i qanday ishlashini ham: tasdiqlash zanjirlari, limitlar, hisobotlar, idempotent to'lovlar. So'nggi oylarda Android'ni joriy stek bo'yicha tizimli yangiladim: Compose, MVI, Coroutines va Flow, Koin, Navigation 3, Room, mobil bank xavfsizligi.

Sizning vakansiyangiz aynan shu kesishmada: Android va korporativ bank mahsuloti. Men jamoaga ham ilova, ham backend bilan muloqotni tushunadigan dasturchi sifatida foyda keltira olaman.»

Raqam va aniq bo'limlar ishonch beradi. Tanaffusni o'zingiz birinchi aytasiz va uni ustunlikka aylantirasiz: backend tajribasi B2B bank ilovasida kamdan-kam uchraydigan narsa.

2Qiyin savollar

«Oxirgi yillarda asosan backend qilgansiz. Android'dan uzoqlashmadingizmi?»

Halol tan oling va darhol dalil bering: «Ha, oxirgi yillarda backend ulushi ko'proq bo'ldi. Lekin Android'ni tashlamadim: ishda ham Android vazifalari bor edi, va so'nggi oylarda joriy stekni tizimli o'rgandim. Masalan, Navigation 3 ning stekni oddiy holat sifatida boshqarishi yoki EncryptedSharedPreferences eskirib, Tink va Keystore'ga o'tilgani...» va bitta mavzuni chuqur gapirib bering. Bu savolga eng yaxshi javob: keyingi texnik savolga juda yaxshi javob berish.

«Compose'da ishlab chiqarishda (production) ishlaganmisiz?»

Yolg'on gapirmang: suhbatchi ikkinchi savol bilan buni darhol biladi. «DigitalBank XML View'larda edi. Compose'ni o'z loyihalarimda va o'qish orqali o'rgandim: rekompozitsiya, barqarorlik, holatni ko'tarish, effektlar.» va bitta tuzoqni (masalan, LaunchedEffect(Unit) va eskirgan parametr) misol qilib ayting. Agar suhbatgacha kichik Compose loyihasini GitHub'ga qo'ysangiz, uni ko'rsating.

«Nega MVVM emas, MVI? Yoki teskari?»

Dogmasiz javob: «MVVM'da bir nechta alohida holat oqimlari bir-biriga zid bo'lib qolishi mumkin. MVI'da bitta o'zgarmas holat, niyatlar va reduktor: har o'zgarish bitta joyda, test oson. Narxi: ko'proq qolip kod. Oddiy ekranda MVVM ham yetadi; bank ekranlarida, ko'p bosqichli formalarda MVI qulayroq.» DigitalBank'da MVVM ishlatilganini aytib, qaysi og'riqlar bo'lganini qo'shing.

«Koin yoki Hilt? Nega?»

«Koin: oddiy DSL, tez yig'ish, Kotlin Multiplatform; zaifligi xatolar ish paytida, buni verify testi yopadi. Hilt: graf kompilyatsiyada tekshiriladi, katta jamoada xavfsizroq, lekin yig'ish sekinroq va qolip ko'proq. Vakansiyada Koin, demak verify testlarini CI'ga qo'yish va bog'liqliklarni faqat konstruktorda olish qoidasini qo'llayman.»

«Kuchsiz tomoningiz nima?»

Haqiqiy, lekin ustida ishlayotgan narsa: «Nazariyani gapirib berish. Amaliyotda qilaman, lekin nega shunday ishlashini tushuntirishga kam e'tibor bergandim. Shuning uchun hozir har bir mavzuni ichkaridan o'rganyapman: masalan, suspend funksiya kompilyatorda holat mashinasiga aylanishi...»

«Qancha maosh kutyapsiz?»

Bozor va vakansiya darajasi (Middle+/Senior) bo'yicha oldindan aniq diapazon tayyorlang va uni xotirjam ayting. Diapazonni birinchi bo'lib aytishni xohlamasangiz: «Vazifalar va jamoa bilan tanishib, sizning diapazoningizni bilsam, aniqroq aytaman».

Og'zaki tekshiruv savollari

Har darsning oxiridagi tekshiruv savollari bir joyda. Variant yo'q: javobni o'z so'zingiz bilan ayting yoki chatga yozing, tekshirib beraman.

A1. Kotlin va Java
  1. Kotlin kodi telefonda ishga tushguncha qaysi bosqichlardan o'tadi?
  2. val x: Int? = 127; val y: Int? = 127. x === y nima beradi? 128 bo'lsa-chi? Nega?
  3. Server javobidagi maydon ba'zan kelmaydi. Kotlin modelida uni qanday e'lon qilasiz va ekranda qanday ko'rsatasiz?
  4. Ekran holati uchun nega sealed interface, karta turi uchun nega enum?
  5. DigitalBank'da qayerda Java va Kotlin aralash ishlatilgan edi, yoki ishlatilganmi? Bu qanday muammo tug'dirdi?
A2. Funksiyalar: lambda, inline, crossinline
  1. Quyidagi kod nimani chop etadi va nega? fun f() { listOf(1, 2, 3).forEach { if (it == 2) return; print(it) }; print("oxiri") }
  2. O'zingiz inline fun ishlat(blok: () -> Unit) yozdingiz va ichida handler.post { blok() } chaqirdingiz. Kompilyator xato beradi. Nega va qanday tuzatiladi?
  3. Nega fun <T> isType(x: Any) = x is T kompilyatsiya bo'lmaydi va qanday tuzatiladi?
  4. Retrofit so'rovini sozlashda apply, javobni ekran modeliga aylantirishda let. Nega aynan shular?
  5. DigitalBank kodida qayerda yuqori tartibli funksiyalar yoki DSL ishlatilgan edi?
A3. Coroutines
  1. Nega suspend funksiya o'zi ekranni qotishdan saqlamaydi? Misol keltiring.
  2. viewModelScope.launch { val a = async { x() }; val b = async { y() } }: x() xato bersa, y() bilan nima bo'ladi? Boshqa launch lar bilan-chi?
  3. Ekran yopildi. Ishlab turgan Retrofit so'rovi bilan nima bo'ladi va nega?
  4. Kodingizda catch (e: Exception) bor. U coroutine ichida qanday xavf tug'diradi?
  5. DigitalBank'da asinxronlik qanday qilingan edi: coroutines, RxJava yoki qayta chaqiruvlar? Farqini suhbatda qanday tushuntirasiz?
A4. Flow: StateFlow va SharedFlow
  1. Room'dan kelgan Flow<List<Karta>> ni ekran holatiga aylantiradigan ViewModel kodini so'z bilan tasvirlang: qaysi operatorlar va qaysi strategiya.
  2. Qidiruv maydoni uchun qaysi uchta operator va nega?
  3. Holatni yangiladingiz, lekin ekran o'zgarmadi. Uchta mumkin bo'lgan sababni ayting.
  4. «To'lov bajarildi» xabari ekran aylantirilganda yo'qolib qoldi. Sababi va yechimi?
  5. lifecycleScope.launch { flow.collect {} } ning xavfi nima?
A5. Arxitektura: Clean, SOLID, MVI
  1. «O'tkazma» ekrani uchun qavatlar va klasslarni sanab bering: har biri qaysi qavatda va nimani biladi?
  2. Domain moduliga Retrofit bog'liqligini qo'shish nega yomon?
  3. Ekran holatini MVI uchun data class qilib yozing: qaysi maydonlar?
  4. To'lov muvaffaqiyatli bo'lgach boshqa ekranga o'tish kerak. Buni holatda yoki effektda qilasizmi, va nega?
  5. SOLID ning qaysi tamoyilini DigitalBank'da buzilganini ko'rgansiz yoki o'zingiz to'g'ri qo'llagansiz?
A6. Dependency Injection: Hilt va Koin
  1. OkHttp, Retrofit, CardApi, baza, repozitoriy, use case, ViewModel: har biri uchun Koin'da qaysi e'lon (single, factory, viewModel) va nega?
  2. Karta tafsilotlari ekrani karta ID sini oladi. ViewModel'ga uni Koin orqali qanday berasiz?
  3. Koin bilan ilova yig'ildi, lekin bitta ekran ochilganda qulaydi. Sababi va uni oldini olish?
  4. Nega repozitoriy ichida get() chaqirish yomon?
  5. DigitalBank'da qaysi DI ishlatilgan va uni tanlash sababi nima edi deb o'ylaysiz?
A7. Jetpack Compose
  1. Balans o'zgardi. Ekrandagi qaysi composable'lar qayta chaqiriladi va qaysilari o'tkazib yuboriladi? Nega?
  2. Summa kiritish maydoni holatini qayerda saqlaysiz: remember, rememberSaveable yoki ViewModel? Javobni asoslang.
  3. Ekran ochilganda bir marta analitika hodisasini yuborish kerak. Qaysi API va qaysi kalit bilan?
  4. Ro'yxatdagi kartaning «balansni yashirish» belgisi yangi karta qo'shilgach boshqa kartaga o'tib qoldi. Sababi?
  5. DigitalBank View tizimida yozilganmi? Compose'ga o'tkazishni qanday rejalashtirgan bo'lardingiz?
A8. Navigatsiya: Compose Navigation va Navigation 3
  1. O'tkazma: summa, tasdiqlash, natija. Natija ekranidan «orqaga» qayerga olib borishi kerak va buni qanday ta'minlaysiz?
  2. Push xabardan tranzaksiya tafsilotini ochish: foydalanuvchi hali PIN kiritmagan. Stek qanday ko'rinishda bo'lishi kerak?
  3. Navigation 3 da ViewModel ekranga qanday bog'lanadi?
  4. Nega argument sifatida faqat ID beriladi?
  5. DigitalBank'da navigatsiya qanday qilingan edi (Activity'lar, Fragment'lar, Navigation Component)?
A9. Tarmoq: Retrofit, Ktor, tokenlar
  1. O'tkazma so'rovi interceptorlardan qanday o'tadi? Qaysi interceptorlar bo'lishi kerak?
  2. Ekran ochilganda beshta so'rov 401 oldi. Yangilash kodingiz nima qiladi?
  3. Server javobiga yangi maydon qo'shdi va eski ilova versiyalari qulay boshladi. Sababi va yechimi?
  4. Foydalanuvchi o'tkazma tugmasini bosdi, javob kelmadi (timeout). Ekranda nima ko'rsatasiz va keyin nima qilasiz?
  5. Alipay integratsiyasidagi OAuth token oqimi va mobil ilovadagi token oqimining o'xshash va farqli tomonlari?
A10. Lokal saqlash: Room va DataStore
  1. Kartalar ekrani uchun Entity, DAO metodlari va repozitoriyning ishlash tartibini tasvirlang.
