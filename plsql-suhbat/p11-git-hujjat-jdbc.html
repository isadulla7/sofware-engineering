P11. Git, hujjatlashtirish va ilova bilan integratsiya (Java, JDBC)

Savol: PL/SQL kodi bazada yashaydi, unda «kim, qachon, nimani o'zgartirdi» qayerda yoziladi? Ikki dasturchi bitta paketni o'zgartirsa nima bo'ladi? Kod test bazasidan prodga qanday yetib boradi? Va Java ilova bazaga qanday ulanadi, protsedurani qanday chaqiradi, xatoni qanday ushlaydi, tranzaksiyani kim boshqaradi?

Bu nima

Git: versiyalarni boshqarish tizimi. Har o'zgarish (commit) muallifi, vaqti va izohi bilan saqlanadi, istalgan eski holatga qaytish mumkin, ko'p odam bir vaqtda parallel ishlaydi. Hujjatlashtirish: kod nima qilishi, nega shunday qilingani va qanday ishlatilishini yozib qoldirish. JDBC (Java Database Connectivity): Java dan bazaga ulanish, SQL yuborish va PL/SQL chaqirishning standart yo'li.

O'xshatish: Git — kitobning har bir tahririni saqlaydigan nashriyot arxivi, kim qaysi sahifani qachon o'zgartirgani bilan. Hujjat — kitobning mundarijasi va so'zboshisi. JDBC — kutubxonaga telefon liniyasi: Java qo'ng'iroq qiladi (ulanish), savol beradi (SQL), javobni qism-qism oladi (ResultSet), oxirida go'shakni qo'yadi (close).

Qayerda ishlatiladi

  • Har kungi ish: paket o'zgartirish, branch, pull request, kod review, test va prod ga chiqarish.
  • Ilova qavati: veb-ekranlar, mobil shlyuz va servislar bazadagi API paketlarini JDBC orqali chaqiradi (P10 dagi qavatlar).
  • Jamoa: yangi xodim kodni hujjat va commit tarixi orqali tushunadi; auditor «bu o'zgarish qachon va kimning topshirig'i bilan» deb so'raydi.
  • Suhbatda: vakansiyada «Git, hujjatlashtirish, Java bilan integratsiya» talablari bor; bu dars shularga javob.

Bu darsning maqsadi

  • Git ning asosiy tushunchalarini (commit, branch, merge, konflikt, pull request, teg) PL/SQL ishida ko'rsatish;
  • baza kodini fayl sifatida saqlash, migratsiya skriptlari va yetkazish (deploy) jarayoni;
  • yaxshi hujjat: paket spec izohlari, COMMENT ON, README, o'zgarishlar jurnali;
  • JDBC: ulanishlar puli, PreparedStatement, CallableStatement, fetch size, batch, tranzaksiya va xatolar.

Bu dars qamraydi

  • Git: repository, commit, branch, merge, rebase, konflikt, pull request, teg, .gitignore
  • Baza kodi faylda: spec va body alohida fayl, migratsiya skriptlari, Flyway va Liquibase g'oyasi
  • Deploy: CI, test sxema, utPLSQL, invalid obyektlar, ORA-04068, rollback rejasi
  • Hujjat: spec izohlari, COMMENT ON TABLE va COLUMN, README, CHANGELOG, qaror yozuvi
  • JDBC: Connection, ulanishlar puli, PreparedStatement, CallableStatement, REF CURSOR, ResultSet, fetch size, batch
  • Tranzaksiya Java da: autocommit, commit va rollback, kim chegarani belgilaydi; SQLException va ORA kodlari

Bu darsga kirmaydi

  • Java tilining o'zi, Spring va Hibernate batafsil
  • Git ning ichki tuzilishi (obyektlar, packfile) batafsil
  • CI serverlarni sozlash (Jenkins, GitLab CI) batafsil

1. Og'riqKod bazada, tarix esa hech qayerda

PL/SQL kodi bazada saqlanadi: CREATE OR REPLACE PACKAGE BODY eski versiyani so'zsiz almashtiradi. Bazaning o'zi «kecha bu paket qanday edi» degan savolga javob bermaydi. Git bo'lmagan jamoada odatda shunday bo'ladi:

  • ikki dasturchi dev bazada bitta paketni ochadi, birinchisi saqlaydi, ikkinchisi o'z nusxasini saqlaganda birinchining ishi jim o'chadi;
  • prod dagi paket test dagidan farq qiladi, lekin qaysi qatorlari va nega, hech kim bilmaydi («drift»);
  • chiqarishdan keyin xato chiqdi, qaytarish kerak, lekin oldingi versiya faqat kimningdir kompyuteridagi «pkg_kredit_final_2_yangi.sql» faylida.

Ilova tomonda ham o'z og'rig'i bor. Har so'rovda yangi ulanish ochish (tarmoq, autentifikatsiya, sessiya yaratish) o'nlab millisekund oladi va baza minglab sessiyadan qiynaladi. SQL ni satr ulab yasash SQL injection ga va har so'rovda hard parse ga olib keladi (P6). Yopilmagan ulanish puldan «oqib ketadi», va bir kun ilova «ulanish yo'q» deb to'xtaydi. Java da autocommit odatda yoqilgan: ikki protsedura chaqiruvi ikki alohida tranzaksiya bo'lib qoladi, va ikkinchisi xato bersa birinchisi allaqachon saqlangan. Bu dars aynan shu muammolarning yechimlari haqida.

2. IchkaridaGit, deploy, hujjat, JDBC

Git asoslari

Repository (repo): loyihaning barcha fayllari va butun o'zgarishlar tarixi. Har dasturchida repo ning to'liq nusxasi bor (Git taqsimlangan tizim), markaziy nusxa esa serverda (GitLab, GitHub, Bitbucket). Commit: bir paytdagi holatning surati: qaysi fayllar qanday o'zgargani, muallif, vaqt va izoh. Branch (tarmoq): commitlar zanjiriga ko'rsatkich; asosiy branch odatda main, har vazifa uchun alohida branch ochiladi va tayyor bo'lganda qaytib qo'shiladi (merge). Ikki branch bitta faylning bitta qatorini turlicha o'zgartirsa, Git o'zi hal qila olmaydi: konflikt, uni dasturchi qo'lda hal qiladi. Pull request (GitLab da merge request): «mening branchimni main ga qo'shing» degan so'rov, unda boshqalar o'zgarishni ko'rib chiqadi (review) va avtomatik tekshiruvlar ishlaydi. Teg: muayyan commitga doimiy nom, odatda versiya raqami (v1.4). Qadamlarni bosing:

Ikki muhim tushuncha. Merge ikki tarixni birlashtiruvchi yangi commit yaratadi, tarix rost qoladi, lekin chiziqlar chalkashadi. Rebase sizning commitlaringizni main ning oxiriga «ko'chirib» qayta yozadi: tarix to'g'ri chiziq, lekin commitlar yangi identifikator oladi. Qoida: rebase faqat o'zingizning, hali hech kim olmagan branchingizda; umumiy branchda tarixni qayta yozmang (push --force hamkasblarning ishini buzadi). Yaxshi commit kichik, bitta mantiqiy o'zgarish va tushunarli izoh bilan: «KR-112: kunlik foizda kunlar soni 365 ga o'tkazildi», «tuzatishlar» emas.

Baza kodi fayl sifatida

Git fayllar bilan ishlaydi, shuning uchun bazadagi har obyekt repoda faylga aylanadi. Odatiy tuzilma:

repo/
├── packages/
│   ├── kredit_foiz.pks          -- paket spec (interfeys)
│   └── kredit_foiz.pkb          -- paket body (amalga oshirish)
├── views/      triggers/      types/
├── migrations/                  -- jadval va ma'lumot o'zgarishlari, tartib bilan
│   ├── V1.4.0_01__kredit_stavka_kun_soni.sql
│   └── V1.4.0_02__lugat_yangi_tur.sql
├── tests/                       -- utPLSQL testlari
├── docs/       README.md       CHANGELOG.md
└── .gitignore

Ikki turdagi kod farqli boshqariladi. Qayta yaratiladigan obyektlar (paket, view, trigger, funksiya): fayl doim obyektning to'liq joriy holati, CREATE OR REPLACE bilan, istalgan marta ishlatsa bo'ladi. Holatli obyektlar (jadval, indeks, ma'lumot): ularni «qayta yaratib» bo'lmaydi, chunki ichida ma'lumot bor. Ular uchun migratsiya skriptlari: har biri bitta o'zgarish (ALTER TABLE ... ADD), tartib raqami bilan, bir marta qo'llanadi. Flyway va Liquibase kabi vositalar bazada jurnal jadvali yuritadi: qaysi skript qachon qo'llangan, uning nazorat summasi, va har yetkazishda faqat yangilarini ishga tushiradi. Skriptlarni iloji boricha idempotent yozish foydali: ikkinchi marta ishga tushsa xato bermaydi (ustun allaqachon bormi, avval tekshiradi).

Kodni prodga yetkazish

Yetkazish (deploy) yo'li bir necha darvozadan o'tadi, va har darvoza xatoni prod dan oldin ushlash uchun. Qadamlarni bosing:

Baza kodini yetkazishning o'ziga xos xavflari bor. DDL avtomatik COMMIT qiladi (P8): migratsiya o'rtasida xato bo'lsa, oldingi DDL lar qaytmaydi, shuning uchun har skript kichik va rollback skripti oldindan yozilgan bo'lishi kerak. Paket body o'zgarganda unga bog'liq obyektlar INVALID bo'lishi mumkin; yetkazishdan keyin qayta kompilyatsiya qilinadi va invalid obyektlar ro'yxati nolga tushganini tekshiriladi. Paket holati (global o'zgaruvchilar) bo'lsa, ulanishlar pulidagi eski sessiyalar keyingi chaqiruvda ORA-04068 oladi (P4): shuning uchun paketlarni iloji boricha holatsiz yozish, yoki ilova bu xatoda bir marta qayta urinishi kerak. To'xtovsiz ishlash kerak bo'lgan tizimlar uchun Oracle da Edition-Based Redefinition bor: yangi kod yangi «edition» da, eski sessiyalar eski versiyada ishlab turadi.

Hujjatlashtirish: kim uchun va qayerda

Hujjatning uch o'quvchisi bor: kodni chaqiradigan dasturchi (nima qiladi, qanday chaqiriladi), kodni o'zgartiradigan dasturchi (nega shunday yozilgan), va biznes yoki auditor (qaysi qoida qayerda). Har biriga o'z joyi:

  • Paket spec: interfeys hujjati. Har ochiq protsedura ustida qisqa izoh: vazifasi, parametrlari, qaytaradigan qiymat, qaysi xatolarni chiqaradi, COMMIT qiladimi.
  • Body ichida: «nima» emas, «nega»: «365 kun, chunki Markaziy bank yo'riqnomasi bo'yicha», «bu yerda FOR UPDATE NOWAIT, chunki kartoteka jobi bilan to'qnashuv bo'lgan».
  • Lug'at izohlari: COMMENT ON TABLE va COMMENT ON COLUMN. Ular bazaning o'zida, ALL_TAB_COMMENTS va ALL_COL_COMMENTS dan o'qiladi va hisobot yoki DWH tahlilchilari uchun eng foydali hujjat.
  • Repo da: README (modul nima, qanday o'rnatiladi, qanday test qilinadi), CHANGELOG (har versiyada nima o'zgardi), qaror yozuvlari (nega shunday arxitektura tanlangan), ER chizmasi.
  • Commit va pull request izohlari: vazifa raqami bilan. Bir yildan keyin «nega bu qator shunday» degan savolga git blame commitni, commit esa vazifani ko'rsatadi.
CREATE OR REPLACE PACKAGE kredit_foiz AS

  -- Qaytaradi    : hisoblangan foiz summasi, tiyinda
  -- Xatolar      : -20101 shartnoma topilmadi, -20102 shartnoma yopiq
  -- Tranzaksiya  : COMMIT qilmaydi, chaqiruvchi boshqaradi

END kredit_foiz;

JDBC: Java bazaga qanday ulanadi

JDBC bir nechta interfeysdan iborat, ularni Oracle drayveri (ojdbc jar) amalga oshiradi. Connection: bazadagi bitta sessiya. PreparedStatement: ? belgili SQL, qiymatlar alohida bind qilinadi. CallableStatement: PL/SQL protsedura yoki funksiyani chaqirish, IN, OUT va REF CURSOR parametrlari bilan. ResultSet: so'rov natijasi, qatorlar tarmoq orqali bo'lak-bo'lak keladi. Ulanishni har so'rovda ochmaslik uchun ulanishlar puli (connection pool: HikariCP, Oracle UCP) ishlatiladi: ilova ishga tushganda bir nechta ulanish ochiladi va ular qayta-qayta «ijaraga» beriladi. Bitta chaqiruvning yo'lini qadam-baqadam ko'ring:

Kodda bu shunday ko'rinadi. try (...) (try-with-resources) ulanish, statement va ResultSet ni xato bo'lsa ham avtomatik yopadi, puldan olingan ulanish esa «yopilganda» aslida pulga qaytadi:

String sql = "SELECT hisob, qoldiq FROM hisoblar WHERE filial = ? AND mijoz_id = ?";
try (Connection c = dataSource.getConnection();            // puldan olish
     PreparedStatement ps = c.prepareStatement(sql)) {
    ps.setString(1, filial);                                // bind: matn bir xil, qiymat har xil
    ps.setLong(2, mijozId);
    ps.setFetchSize(500);                                   // bitta borishda 500 qator
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            royxat.add(new Hisob(rs.getString("hisob"), rs.getBigDecimal("qoldiq")));
        }
    }
}                                                           // ulanish pulga qaytadi

PL/SQL protsedurani chaqirish, OUT parametr va REF CURSOR bilan. Tranzaksiya chegarasini Java belgilaydi:

try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);                                 // ikki chaqiruv = bitta tranzaksiya
    try (CallableStatement cs = c.prepareCall("{ call kredit_api.berish(?, ?, ?, ?) }")) {
        cs.setLong(1, arizaId);
        cs.setBigDecimal(2, summa);
        cs.registerOutParameter(3, Types.NUMERIC);          // OUT: yangi kredit id
        cs.registerOutParameter(4, OracleTypes.CURSOR);     // OUT: grafik, REF CURSOR
        cs.execute();
        long kreditId = cs.getLong(3);
        try (ResultSet g = (ResultSet) cs.getObject(4)) { /* grafikni o'qish */ }
        c.commit();
    } catch (SQLException e) {
        c.rollback();
        if (e.getErrorCode() == 20102) throw new BiznesXato("Shartnoma yopiq");   // ORA-20102
        throw e;
    }
}

Fetch size va tarmoqqa borishlar

ResultSet qatorlarni bir yo'la emas, bo'laklab oladi: har bo'lak bitta tarmoq «borib kelishi» (round trip). Oracle JDBC drayverida standart fetch size 10. 100 ming qatorli hisobot 10 ming marta borib keladi, va har biri tarmoqda kamida millisekund. Qator sonini o'zgartiring:

Yozishda ham xuddi shu g'oya: batch. Ming qatorni ming marta executeUpdate() bilan emas, addBatch() bilan yig'ib, bitta executeBatch() da yuboriladi. Bu Java tomondagi FORALL (P5). Juda katta hajmda esa ma'lumotni Java ga olib kelmasdan, bitta PL/SQL chaqiruvi bazaning o'zida qayta ishlaydi: ma'lumotga yaqinlik (P10).

Turlar mosligi va ORM

  • NUMBER → BigDecimal. Pul uchun hech qachon double emas: 0.1 + 0.2 ikkilik kasrda aniq emas.
  • DATE → LocalDateTime yoki Timestamp: Oracle DATE da vaqt ham bor (P1).
  • VARCHAR2 → String; CLOB va BLOB oqim (stream) sifatida; REF CURSOR → ResultSet; Oracle kolleksiya turlari → massiv (ARRAY), ular bilan bitta chaqiruvda ko'p qator yuborish mumkin.
  • NULL: getLong() NULL uchun 0 qaytaradi; farqlash uchun wasNull() yoki getObject().

Ko'p Java loyihalarida JDBC ustida qatlam bor: Spring JdbcTemplate (ulanish va yopishni o'zi boshqaradi) yoki JPA va Hibernate (ORM: jadval qatorini Java obyektiga avtomatik moslash). ORM oddiy CRUD uchun qulay, lekin murakkab hisobot va katta hajmda u yasagan SQL ni nazorat qilish kerak (N+1 muammosi: ro'yxatdagi har obyekt uchun alohida so'rov). Bank yadrosida odatda biznes mantiq PL/SQL da, Java esa uni CallableStatement yoki JdbcTemplate orqali chaqiradi.

5. AmaliyotdaTuzoqlar

Tuzoq: to'g'ridan-to'g'ri bazada tahrirlash

Dasturchi xatoni prod da IDE orqali paket body ni o'zgartirib tuzatdi. Repo da eski versiya qoldi. Keyingi chiqarishda repo dagi versiya yetkazildi va tuzatish jim yo'qoldi, xato qaytdi.

To'g'risi: yagona manba repo; har o'zgarish branch va commit orqali, shoshilinch bo'lsa ham hotfix branchi bilan. Muntazam drift tekshiruvi: bazadagi kod repo bilan solishtiriladi.

Tuzoq: satr ulab SQL yasash

"... WHERE hisob = '" + hisob + "'". Har qiymat yangi SQL matni: shared pool to'ladi, har so'rov hard parse (P6). Foydalanuvchi ' OR '1'='1 kiritsa, so'rov hamma qatorni qaytaradi.

To'g'risi: PreparedStatement va bind (?). Jadval yoki ustun nomi o'zgaruvchi bo'lsa, ruxsat etilgan ro'yxatdan tekshirish (PL/SQL da DBMS_ASSERT, P5).

Tuzoq: yopilmagan ulanish

Xato yo'lida close() chaqirilmaydi. Har xatoda puldan bitta ulanish yo'qoladi, bir necha soatdan keyin pul bo'sh, ilova «Connection is not available, request timed out» bilan to'xtaydi, bazada esa sessiyalar ochiq qolgan.

To'g'risi: har doim try-with-resources; pulda oqish aniqlash (leak detection) sozlamasi; bazada V$SESSION da uzoq «INACTIVE» sessiyalarni kuzatish.

Tuzoq: autocommit yoqilgan holda bir necha chaqiruv

Java ketma-ket ikki protsedurani chaqirdi: hisobdan yechish va boshqa hisobga yozish. Autocommit yoqilgan: birinchisi darhol saqlandi, ikkinchisi xato berdi, pul «yo'lda» qoldi.

To'g'risi: setAutoCommit(false) (yoki Spring da @Transactional) va bitta commit; yaxshisi, ikkala amalni bitta PL/SQL API protsedurasiga birlashtirish.

Tuzoq: standart fetch size bilan katta hisobot

Hisobot 2 million qator o'qiydi, fetch size 10: 200 ming borib kelish. Bazada so'rov 5 soniyada tugadi, foydalanuvchi esa 4 daqiqa kutdi; AWR da «SQL*Net message from client» kutishi.

To'g'risi: katta o'qishda fetch size 500 dan 1000 gacha (xotiraga mos), juda katta hajmni esa Java ga olib kelmasdan bazada qayta ishlash.

6. SuhbatdaSavol va namunaviy javoblar

Avval javobni o'zingiz ovoz chiqarib ayting, keyin oching.

PL/SQL kodini qanday versiyalaysiz?

Repo yagona manba. Har paket spec va body alohida faylda, view, trigger, tur ham fayllarda, CREATE OR REPLACE bilan. Jadval va ma'lumot o'zgarishlari esa tartib raqamli migratsiya skriptlarida, chunki jadvalni qayta yaratib bo'lmaydi; ularni Flyway yoki Liquibase kabi vosita yoki o'z jurnal jadvalimiz bilan qo'llaymiz. Har vazifa uchun branch, pull request va review, keyin main ga merge va versiya tegi. Bazada to'g'ridan-to'g'ri tahrir qilinmaydi, va vaqti-vaqti bilan bazadagi kod repo bilan solishtiriladi.

Merge va rebase farqi nima?

Merge ikki tarixni birlashtiruvchi yangi commit qo'shadi: tarix rost, kim qachon nimani qo'shgani ko'rinadi, lekin grafik chalkashadi. Rebase mening commitlarimni asos branchning oxiriga qayta yozadi: tarix to'g'ri chiziq, lekin commitlar yangi identifikator oladi. Shuning uchun rebase faqat o'z, hali push qilinmagan yoki faqat menda bo'lgan branchda; umumiy branchda tarixni qayta yozmayman.

Konfliktni qanday hal qilasiz?

Avval main ni o'z branchimga olib kelaman (merge yoki rebase). Git konfliktli joylarni <<<<<<<, =======, >>>>>>> belgilari bilan ko'rsatadi. Ikkala o'zgarishning maqsadini tushunaman, kerak bo'lsa hamkasb bilan gaplashaman, to'g'ri variantni qoldiraman, paketni test bazada kompilyatsiya qilib testlarni ishga tushiraman, keyin commit. Konfliktlarni kamaytirish uchun: kichik va tez-tez birlashtiriladigan branchlar, va main ni o'z branchimga muntazam olib kelish.

Baza o'zgarishini prodga qanday chiqarasiz? Xato bo'lsa nima qilasiz?

Chiqarish paketi: tartiblangan migratsiya skriptlari va o'zgargan obyektlar, har biri uchun rollback skripti, va qo'llash tartibi. Avval test bazada aynan shu paket qo'llanadi va tekshiriladi. Prod da kelishilgan oynada, DBA bilan: skriptlar, qayta kompilyatsiya, invalid obyektlar nolmi, tutun testi (asosiy ekran va job ishlaydimi). Xato bo'lsa rollback rejasi: paketlar oldingi versiyaga (repo dagi oldingi teg), jadval o'zgarishlari teskari skript bilan. DDL avtomatik commit qilishini hisobga olib, skriptlar kichik bo'ladi. Paket holati bo'lsa ORA-04068 ni oldindan ilova jamoasi bilan kelishaman.

Yaxshi hujjat qanday bo'ladi?

O'quvchiga qarab. Chaqiruvchi uchun paket spec da har protsedura ustida: vazifasi, parametrlar, qaytadigan qiymat, xato kodlari, COMMIT qiladimi. O'zgartiruvchi uchun body da «nega»: biznes qoida yoki nozik joy sababi. Tahlilchi uchun bazada COMMENT ON TABLE va COLUMN. Jamoa uchun repo da README, CHANGELOG va arxitektura qarorlari. Va commit izohlarida vazifa raqami. Eskirgan hujjat hujjatsizlikdan yomon, shuning uchun hujjat kod bilan bitta pull request da yangilanadi.

Java dan PL/SQL protsedurani qanday chaqirasiz?

CallableStatement: { call paket.protsedura(?, ?, ?) }, funksiya uchun { ? = call paket.funksiya(?) }. IN parametrlar set metodlari bilan, OUT lar registerOutParameter bilan oldindan ro'yxatga olinadi, execute() dan keyin get bilan o'qiladi. Ro'yxat qaytarish uchun REF CURSOR OUT parametri, Java da ResultSet bo'lib keladi. Ko'p qatorni yuborish uchun Oracle kolleksiya turi va ARRAY. Xatoni SQLException orqali olaman, getErrorCode() ORA raqamini beradi: masalan RAISE_APPLICATION_ERROR(-20102) dan 20102, uni biznes xatoga aylantiraman.

Ulanishlar puli nima uchun kerak va qanday sozlanadi?

Fizik ulanish ochish qimmat: TCP, autentifikatsiya, sessiya va server jarayoni yaratish. Pul ilova boshlanganda bir nechta ulanish ochadi va ularni so'rovlarga ijaraga beradi, ulanish «yopilganda» pulga qaytadi. Asosiy sozlamalar: maksimal hajm (baza ko'tara oladigan sessiyalar va ilova oqimlari soniga qarab, odatda katta emas: o'nlab), minimal hajm, kutish vaqti (ulanish bo'lmasa qancha kutish), ulanishni tekshirish, maksimal yashash vaqti, va oqish aniqlash. Pul juda katta bo'lsa baza ko'p parallel sessiyadan qulflar va latch larda qiynaladi.

Java va PL/SQL o'rtasida tranzaksiyani kim boshqaradi?

Eng tashqi chaqiruvchi, odatda Java servis qavati. PL/SQL API protseduralari COMMIT qilmaydi, shunda Java bir nechta chaqiruvni bitta tranzaksiyaga birlashtira oladi. JDBC da autocommit standart yoqilgan, shuning uchun uni o'chirib, oxirida commit, xatoda rollback qilinadi; Spring da @Transactional buni o'zi qiladi. Istisno: audit va xato jurnali avtonom tranzaksiyada (P8), asosiy tranzaksiya qaytsa ham saqlansin.

Fetch size va batch nima beradi?

Ikkalasi ham tarmoqqa borib kelishlarni kamaytiradi. Fetch size: bitta borishda nechta qator olinadi, Oracle drayverida standart 10; katta o'qishda 500 dan 1000 gacha qilinsa, borishlar soni 50 dan 100 martagacha kamayadi. Batch: ko'p INSERT yoki UPDATE ni yig'ib, bitta borishda yuborish, bu Java dagi FORALL. Juda katta hajmda esa ma'lumotni Java ga umuman olib kelmay, bazada bitta SQL yoki PL/SQL chaqiruvi bilan qayta ishlash afzal.

Java dasturchilar bilan qanday hamkorlik qilasiz?

Kelishuv API paketining spec ida: nomlar, parametrlar va turlar, xato kodlari ro'yxati, COMMIT qiladimi, qaytariladigan kursorning ustunlari. Spec o'zgarishi alohida kelishiladi, chunki u ikki tomonni ham buzadi; iloji bo'lsa yangi parametr DEFAULT bilan qo'shiladi, eski chaqiruvlar ishlab turadi. Xatolar uchun yagona diapazon (masalan -20100 dan -20199 kredit moduli) va hujjat. Ularga test baza va namunaviy chaqiruv beraman, sekin chaqiruvlarda esa AWR yoki V$SQL dan SQL_ID va rejani birga ko'ramiz.

Kod review da PL/SQL kodida nimalarga qaraysiz?

Bind ishlatilganmi, satr ulangan dinamik SQL yo'qmi. Sikl ichida SQL yo'qmi (BULK yoki bitta SQL bo'lishi kerakmi). WHEN OTHERS THEN NULL kabi xatoni yutish yo'qmi, xato kodi va kontekst saqlanadimi. API ichida COMMIT yo'qmi. Indekslar va partitsiya kalitlari shartda ishlatiladimi, rejasi tekshirilganmi. Qulflar tartibi va NOWAIT yoki timeout. Migratsiya skripti va rollback bormi, idempotentmi. Spec izohlari va CHANGELOG yangilanganmi. Va testlar.

7. Tekshiruv

Javoblarni chatga yozing.

  1. Siz va hamkasb bitta paket body ni o'zgartirdingiz. U birinchi bo'lib main ga birlashtirdi. Siz nima qilasiz, qaysi buyruqlar bilan, va konflikt chiqsa uni qanday tekshirasiz?
  2. Yangi vazifa: hisoblar jadvaliga «yopilish sababi» ustuni va uni to'ldiradigan paket o'zgarishi. Repo da qaysi fayllar paydo bo'ladi yoki o'zgaradi, qanday tartibda qo'llanadi, rollback qanday?
  3. Java kodida: stmt.executeQuery("SELECT * FROM mijozlar WHERE inn = '" + inn + "'"). Uchta muammoni ayting va tuzatilgan variantni yozing.
  4. Prod ga chiqarishdan keyin bir necha daqiqa ilova loglarida ORA-04068 chiqdi, keyin yo'qoldi. Nima bo'ldi, nega o'zi yo'qoldi, keyingi safar qanday oldini olasiz?
  5. Java servisi ikki protsedurani chaqiradi: kredit berish va pulni mijoz hisobiga o'tkazish. Tranzaksiyani to'g'ri qilib yozing (psevdokod yetarli) va xato kodi -20102 ni biznes xatoga aylantiring.

Chuqurroq

Branch strategiyalari

Trunk-based: hamma qisqa branchlarni tez-tez main ga birlashtiradi, main doim chiqarishga tayyor. Git Flow: main (prod), develop (keyingi versiya), feature, release va hotfix branchlari. Bank kabi kamdan-kam va rejali chiqarishlar bo'ladigan joylarda release va hotfix branchlari keng tarqalgan; shoshilinch tuzatish chiqarilgan versiya tegidan ochiladi va keyin main ga ham qaytariladi, aks holda keyingi versiyada xato qaytadi.

utPLSQL bilan test

Test paketi annotatsiyalar bilan yoziladi. Har test oldidan ma'lumot tayyorlanadi, test oxirida avtomatik rollback (test bazani ifloslamaydi):

CREATE OR REPLACE PACKAGE test_kredit_foiz AS
  --%suite(Kredit foizi)
  --%test(365 kunlik yilda bir kunlik foiz)
  PROCEDURE bir_kunlik_foiz;
END;
/
CREATE OR REPLACE PACKAGE BODY test_kredit_foiz AS
  PROCEDURE bir_kunlik_foiz IS
  BEGIN
    -- 10 000 000 so'm, 24% yillik, 365 kun: 6 575.34
    ut.expect(kredit_foiz.hisobla_summa(1000000000, 24, 365)).to_equal(657534);
  END;
END;
/
EXEC ut.run('test_kredit_foiz');
Ulanish tarmog'i: listener, xizmat nomi, URL

JDBC URL: jdbc:oracle:thin:@//host:1521/xizmat_nomi. «thin» drayver to'liq Java da, mijoz dasturi kerak emas. Listener 1521 portda tinglaydi va so'rovni xizmat nomiga qarab baza instansiyasiga uzatadi, keyin sessiya va server jarayoni yaratiladi. RAC da bir nechta instansiya bitta xizmat nomi ostida, ulanishlar ular orasida taqsimlanadi. Parollar kodda yoki repo da emas, sozlama yoki maxfiy saqlagichda.
