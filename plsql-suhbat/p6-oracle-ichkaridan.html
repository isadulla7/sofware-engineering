Yo'l xaritasi / Oracle PL/SQL

P6. Oracle ichkaridan: SGA va PGA, fon jarayonlari, so'rov qanday bajariladi, parse va bind

Savol: siz SELECT yoki COMMIT yuborgan paytdan javob kelguncha Oracle ichida nima bo'ladi? Ma'lumot qayerda turadi, kim uni diskka yozadi, elektr o'chsa nima yo'qoladi, va nega bitta so'rovni literal bilan yozish butun serverni sekinlashtiradi?

Sodda tilda: 15 daqiqada

Bu qism darsning eng kerakli joylari, oddiy so'z bilan. Har g'oya bir xil tartibda: hayotiy misol, bitta qoida, kichik misol va suhbatda aytadigan tayyor javob. Avval shuni o'qing. Pastdagi batafsil qism keyin, "nega shunday" degan savolga javob kerak bo'lganda.

1. Instance va database: oshxona va ombor

Restoranda ombor (oziq-ovqat saqlanadi) va oshxona (pishiriladi, oshpazlar ishlaydi) bor. Oshxona yopilsa ham ombordagi narsalar qoladi.

Qoida: Database: diskdagi fayllar (ma'lumot, redo log, control file). Instance: xotira (SGA) va fon jarayonlari. Instance o'chsa fayllar qoladi.

SELECT instance_name, status FROM v$instance;

Suhbatda: "Database fayllar, instance xotira va jarayonlar. Bitta database ni RAC da bir nechta instance ochishi mumkin."

2. SGA: hamma uchun umumiy xotira

Oshxonadagi umumiy stol: tez-tez kerak bo'ladigan narsalar shu yerda turadi, har safar omborga borilmaydi.

Qoida: SGA ichida asosiylari: buffer cache (o'qilgan bloklar), shared pool (tahlil qilingan SQL va rejalar), redo log buffer (o'zgarishlar yozuvi).

SELECT name, bytes FROM v$sgainfo;

Suhbatda: "SGA umumiy xotira: buffer cache, shared pool, redo buffer. PGA esa har sessiyaning shaxsiy xotirasi."

3. PGA: har ishchining shaxsiy stoli

Har oshpazning o'z kesish taxtasi. Katta ish sig'masa, vaqtincha yerga (TEMP ga) qo'yadi va sekinlashadi.

Qoida: Saralash, GROUP BY, hash join PGA da bajariladi. Sig'masa TEMP tablespace ga (diskka) yoziladi.

SELECT name, value FROM v$pgastat WHERE name LIKE 'total PGA%';

Suhbatda: "Saralash va hash join PGA da; sig'masa TEMP ga tushadi va so'rov sekinlashadi."

4. COMMIT tez, chunki faqat "jurnal" yoziladi

Bankda kassir avval jurnalga "Aliga 100 ming berildi" deb yozadi. Seyfni tartiblash keyinroq. Chiroq o'chsa ham jurnal bo'yicha hammasi tiklanadi.

Qoida: COMMIT da LGWR redo yozuvlarini diskka yozadi. O'zgargan bloklarni DBWn keyinroq yozadi. Yiqilsa, redo bo'yicha tiklanadi.

COMMIT;   -- LGWR: redo diskka; bloklar esa keyin, DBWn yozadi

Suhbatda: "COMMIT redo log yozilganda tugaydi (write-ahead logging), bloklar keyin yoziladi. Yiqilishda SMON redo dan tiklaydi."

5. SQL ning yo'li: parse, execute, fetch

Taksiga manzil aytasiz: haydovchi yo'lni o'ylaydi (parse), yuradi (execute), sizni tushiradi (fetch).

Qoida: Parse: matnni tekshirish va reja tuzish. Execute: bajarish. Fetch: natija qatorlarini qaytarish.

-- bir xil SQL ikkinchi marta kelsa reja shared pool dan olinadi

Suhbatda: "So'rov parse, execute va fetch bosqichlaridan o'tadi; reja shared pool da saqlanadi va qayta ishlatiladi."

6. Hard parse qimmat, soft parse arzon

Har safar yangi manzil: haydovchi xaritani ochib o'ylaydi (hard). Tanish manzil: darhol yo'lga tushadi (soft).

Qoida: Yangi SQL matni uchun reja noldan tuziladi (hard parse). Matn bir xil bo'lsa tayyor reja olinadi (soft parse).

SELECT ... WHERE id = 123;   -- har id yangi matn: hard parse
SELECT ... WHERE id = :id;   -- bitta matn: soft parse

Suhbatda: "Hard parse CPU va qulflarni talab qiladi. Bind o'zgaruvchilar matnni bir xil qilib, soft parse beradi."

7. Bind o'zgaruvchi: qiymat o'rniga "bo'sh katak"

Bir xil blanka, faqat ism katagi har xil. Yangi blanka chop etish shart emas.

Qoida: Qiymatni SQL matniga yozmay, :nom yoki ? bilan alohida berish. Reja qayta ishlatiladi va SQL injection bo'lmaydi.

PreparedStatement ps = c.prepareStatement("SELECT qoldiq FROM hisoblar WHERE hisob = ?");

Suhbatda: "Bind bilan bitta reja hamma qiymat uchun, shared pool to'lmaydi va injection yo'q."

O'zingizni tekshiring: yuqoridagi 7 ta "Suhbatda" gapini ko'rmasdan ayta olsangiz, P6 ning asosi sizda bor. Qolgani pastda, chizmalar va chuqurroq tushuntirish bilan.

Bu nima

Instance bu ishlab turgan Oracle: xotira (SGA, hamma sessiyalar uchun umumiy) va fon jarayonlari. Database (baza) esa diskdagi fayllar: ma'lumot fayllari, redo log, control file. Instance o'chsa, baza qoladi; baza fayllari bo'lmasa, instance ishga tusha olmaydi.

O'xshatish: restoran. Baza bu ombor: hamma mahsulot shu yerda, lekin olib kelish sekin. SGA bu oshxona stoli: tez-tez kerak bo'ladigan mahsulot (buffer cache) va tayyor retseptlar kitobi (shared pool) shu yerda. Oshpazlar (server jarayonlari) har biri o'z kichik stoli (PGA) bilan ishlaydi. Yordamchilar (fon jarayonlari) idishlarni omborga qaytaradi, buyurtma daftarini yuritadi, tartibni saqlaydi.

Qayerda ishlatiladi

  • Tezlik muammolari: «tizim sekin» degan shikoyatni tahlil qilish doim shu yerdan boshlanadi: qattiq parse ko'pmi, diskdan o'qish ko'pmi, sessiyalar nimani kutyapti.
  • Ilova kodi: Java'da PreparedStatement va bind, ulanishlar puli (connection pool), kursorni yopish: bularning hammasi shared pool va jarayonlar bilan bog'liq.
  • Ishonchlilik: COMMIT nega kafolat beradi, server yiqilsa nima tiklanadi: bank uchun eng muhim savol.
  • Suhbatda: «SGA va PGA farqi», «qattiq va yumshoq parse», «bind o'zgaruvchi nima uchun» deyarli har Oracle suhbatida so'raladi.

Bu darsning maqsadi

  • instance va baza, SGA va PGA tarkibini chizib bera olish;
  • asosiy fon jarayonlari (DBWn, LGWR, CKPT, SMON, PMON, ARCn) nima qilishini aytish;
  • SELECT, UPDATE va COMMIT ning ichkaridagi yo'lini qadam-baqadam tushuntirish;
  • parse bosqichlari, qattiq va yumshoq parse, bind o'zgaruvchilar va bind peeking;
  • logical va physical read, PGA dagi saralash va TEMP ga tushish.

Bu dars qamraydi

  • Instance va database, dedicated va shared server
  • SGA: buffer cache, shared pool (library cache, dictionary cache), redo log buffer, large pool, Java pool
  • PGA: sessiya xotirasi, sort va hash work area, TEMP
  • Fon jarayonlari: DBWn, LGWR, CKPT, SMON, PMON, ARCn, MMON
  • SELECT, UPDATE, COMMIT, checkpoint va tiklanish yo'li
  • Parse, optimize, execute, fetch; qattiq, yumshoq va «parse siz»
  • Bind o'zgaruvchilar, CURSOR_SHARING, bind peeking, adaptive cursor sharing
  • Logical va physical read, V$ ko'rinishlari, AWR

Bu darsga kirmaydi

  • Bajarilish rejasini o'qish, indekslar: P7-darsda
  • Undo, redo, qulflar va izolyatsiya batafsil: P8-darsda
  • Jadval, segment, partitsiya tuzilishi: P9-darsda

1. Og'riqDisk sekin, foydalanuvchi ko'p, SQL qimmat

Ma'lumotlar bazasi uch qarama-qarshi talabni bir vaqtda bajarishi kerak, va Oracle'ning ichki tuzilishi aynan shu ziddiyatdan kelib chiqqan.

  • Disk xotiradan ming baravar sekin. Xotiradan blok o'qish mikrosekundning bir qismi, aylanuvchi diskdan o'qish millisekundlar. Agar har so'rov diskka borsa, mingta kassa operatsiyasi navbatga turadi. Demak tez-tez kerak bo'ladigan bloklar xotirada turishi kerak: buffer cache.
  • Xotira esa ishonchsiz. Elektr o'chsa, xotiradagi hamma narsa yo'qoladi. Lekin bank «pul o'tkazildi» degan bo'lsa, bu yo'qolmasligi kerak. Har o'zgarishni darhol diskdagi ma'lumot fayliga yozish esa sekin (tasodifiy joylarga yozish). Yechim: o'zgarishning qisqa yozuvini (redo) ketma-ket faylga tez yozish, bloklarni esa keyinroq, to'plab.
  • SQL ni tushunish qimmat. So'rov matnini tekshirish, jadval va huquqlarni topish, minglab mumkin bo'lgan rejadan eng yaxshisini tanlash: bu CPU vaqti, ba'zan millisekundlar. Bir xil so'rov sekundiga minglab marta kelsa, har safar qaytadan o'ylash isrof. Yechim: tayyor rejalarni hamma sessiya uchun umumiy xotirada saqlash: shared pool.

Shu uch yechim, va ularni boshqaradigan fon jarayonlari, Oracle arxitekturasining asosi. 1980-yillarda Oracle 6 dan boshlab shakllangan va hozirgacha mohiyati o'zgarmagan.

2. IchkaridaInstance, baza va so'rovning yo'li

Instance va baza: kim qayerda

Ilova (masalan Java servisi) Oracle'ga ulanganda, server tomonida unga server jarayoni ajratiladi (dedicated server rejimi, eng ko'p tarqalgan). Ilova faqat SQL matni va qiymatlarni yuboradi, haqiqiy ishni server jarayoni qiladi. Har server jarayonining o'z xususiy xotirasi bor: PGA. Hamma server jarayonlari bitta umumiy xotira bilan ishlaydi: SGA. Fon jarayonlari esa hech bir sessiyaga tegishli emas, ular butun instance uchun ishlaydi.

  • Buffer cache: ma'lumot bloklarining nusxalari (odatda 8 KB). Jadval, indeks va undo bloklari. Kamdan-kam ishlatilgan bloklar yangilariga joy bo'shatadi (LRU ga o'xshash algoritm). Keshda o'zgartirilgan, lekin hali diskka yozilmagan blok dirty (kir) blok deyiladi.
  • Shared pool: library cache (SQL va PL/SQL matnlari, ularning rejalari, kompilyatsiya qilingan paketlar) va dictionary cache (jadval, ustun, huquqlar haqidagi ma'lumotlar, «row cache» ham deyiladi). 11g dan bu yerda result cache ham bor.
  • Redo log buffer: o'zgarishlar yozuvlari (redo), diskka yozilishini kutib turadi. Kichik (megabaytlar), lekin juda tez-tez bo'shatiladi.
  • Large pool, Java pool, streams pool: RMAN zaxira nusxasi, parallel so'rovlar va shared server uchun; bazadagi Java uchun; replikatsiya uchun.
  • PGA: sessiya o'zgaruvchilari, PL/SQL paket holati (P4 dagi paket o'zgaruvchilari shu yerda), kolleksiyalar (P5 dagi BULK COLLECT shu yerda), saralash va hash join uchun ish maydoni.

Pastdagi chizmada to'rt holat. Holatni tanlang, keyin qadamlarni birma-bir bosing: har qadamda qaysi qism ishlayotgani va ma'lumot qayerga ketayotgani ko'rinadi.

Bu chizmadan uchta muhim xulosa. Birinchisi: COMMIT tez, chunki u faqat redo ni yozishni kutadi, o'zgargan bloklarni emas. Redo ketma-ket faylga yoziladi, bu diskning eng tez rejimi. Ikkinchisi: commit qilingan ma'lumot yo'qolmaydi, chunki uning redo si diskda, va instance yiqilsa SMON redo ni qayta qo'llab, bloklarni tiklaydi. Bu «write-ahead logging» tamoyili. Uchinchisi: DBWn ning yozishi COMMIT bilan bog'liq emas: u commit qilinmagan bloklarni ham diskka yozishi mumkin, chunki tiklanishda undo ular ni bekor qiladi.

Logical read va physical read

Server jarayoni blokni har doim buffer cache orqali o'qiydi. Blok keshda bo'lsa, bu logical read (statistikada consistent gets va db block gets). Bo'lmasa, avval diskdan keshga o'qiladi: physical read. Shuning uchun so'rovning narxini baholashda logical read soni asosiy o'lchov: physical read kesh holatiga bog'liq va tasodifiy o'zgaradi, logical read esa so'rov va reja o'zgarmasa barqaror. Sekin so'rovni tezlashtirish deyarli doim logical read sonini kamaytirish demak: yaxshiroq indeks, yaxshiroq reja (P7). «Buffer cache hit ratio 99%» yaxshi ko'rinsa ham, keraksiz millionlab logical read baribir CPU ni yeydi.

So'rov qanday bajariladi: parse, execute, fetch

Har SQL to'rt bosqichdan o'tadi. Parse: matnni tekshirish va reja tayyorlash. Bind: o'zgaruvchilarga qiymat berish. Execute: rejani bajarish (DML da shu yerda qatorlar o'zgaradi). Fetch: SELECT natijasini qatorma-qator yoki to'plab qaytarish. Parse ning ichi:

  1. Sintaksis tekshiruvi: SQL grammatikasi to'g'rimi (SELEC xato).
  2. Semantik tekshiruv: jadval va ustunlar bormi, foydalanuvchining huquqi bormi. Dictionary cache dan.
  3. Shared pool tekshiruvi: SQL matnidan hash hisoblanadi va library cache da xuddi shu matn va mos muhit bilan tayyor kursor qidiriladi. Topilsa: yumshoq parse (soft parse), keyingi ikki qadam o'tkazib yuboriladi.
  4. Optimizatsiya: optimizator statistikaga qarab mumkin bo'lgan rejalarni baholaydi va eng arzonini tanlaydi. Eng qimmat qism.
  5. Row source generation: tanlangan rejadan bajariladigan tuzilma yasaladi va shared pool ga saqlanadi.

3-qadamda topilmasa, 4 va 5 bajariladi: bu qattiq parse (hard parse). U nafaqat CPU, balki shared pool ichidagi umumiy tuzilmalarga qulf (latch va mutex) talab qiladi: bir vaqtda ko'p sessiya qattiq parse qilsa, ular bir-birini kutadi va tizim yadrolar soniga qaramay sekinlashadi. Uchinchi daraja ham bor: ilova kursorni yopmasdan qayta bajarsa (yoki PL/SQL o'z kursor keshida saqlasa), parse umuman bo'lmaydi.

Library cache dagi kursor ikki qavatli. Parent cursor SQL matni bilan aniqlanadi (SQL_ID shu matndan hisoblanadi; V$SQLAREA). Uning ostida bir yoki bir nechta child cursor (V$SQL): har biri o'z rejasi bilan. Matn bir xil bo'lsa ham child har xil bo'lishi mumkin: boshqa sxemadagi bir xil nomli jadval, boshqa optimizator sozlamalari, bind tipi yoki uzunligi juda farq qilsa, adaptive cursor sharing. Nega yangi child yaratilganini V$SQL_SHARED_CURSOR ko'rsatadi.

Bind o'zgaruvchilar: nega bu tezlik va xavfsizlik

Shared pool tekshiruvi matnni harfma-harf solishtiradi. WHERE id = 101 va WHERE id = 102 Oracle uchun ikki xil so'rov, ikki qattiq parse, ikki kursor. Ilova sekundiga mingta to'lovni shunday yuborsa, sekundiga ming qattiq parse va shared pool bir martalik kursorlarga to'ladi. WHERE id = :id esa bitta matn: bitta qattiq parse, keyin hammasi yumshoq. Java'da Statement bilan satr ulash o'rniga PreparedStatement va ?. PL/SQL da statik SQL dagi o'zgaruvchilar avtomatik bind bo'ladi, faqat dinamik SQL da USING kerak (P5).

Bindning bitta nozik joyi bor: bind peeking. 9i dan optimizator qattiq parse paytida bind ning birinchi qiymatiga «mo'ralab», rejani shu qiymat uchun tanlaydi. Agar ma'lumot notekis bo'lsa (99% to'lovlar holat = 'BAJARILDI', 1% 'XATO') va birinchi kelgan qiymat kamyob bo'lsa, indeks bo'yicha reja tanlanadi va keyin ko'p sonli qiymat uchun ham o'sha reja ishlatiladi: so'rov to'satdan sekinlashadi. 11g dagi adaptive cursor sharing buni qisman hal qiladi: bind ga sezgir kursor uchun har xil qiymat diapazonlariga alohida child yaratadi. Shuning uchun bind ishlatilmaydigan yagona holat: kam bajariladigan, uzoq ishlaydigan hisobot so'rovlari, ularda parse narxi ahamiyatsiz va aniq reja muhimroq.

PGA: saralash xotirada sig'masa

ORDER BY, GROUP BY, DISTINCT, hash join, analitik funksiyalar (P2) ish maydoni (work area) talab qiladi, u PGA da. 9i dan Oracle uni avtomatik boshqaradi: PGA_AGGREGATE_TARGET hamma sessiyalar uchun umumiy maqsad, har operatsiya shundan ulush oladi. Ma'lumot sig'masa, uning bir qismi TEMP tablespace ga (diskka) yoziladi. Uch rejim: optimal (hammasi xotirada), one-pass (bir marta diskka yozib, bir marta o'qish), multi-pass (bir necha marta, juda sekin). Sinab ko'ring:

TEMP ga tushgan saralash V$SQL_WORKAREA va rejadagi TempSpc ustunida ko'rinadi. TEMP tugasa: ORA-01652: unable to extend temp segment. 12c dan PGA_AGGREGATE_LIMIT PGA ga qat'iy chegara qo'yadi: undan oshgan sessiyalar to'xtatiladi (ORA-04036). LIMIT siz BULK COLLECT (P5) aynan shu chegaraga uriladi.

Ichkariga qanday qaraladi

  • V$SESSION: kim ulangan, hozir nima qilyapti, nimani kutyapti (EVENT, SQL_ID, BLOCKING_SESSION).
  • V$SQL, V$SQLAREA: shared pool dagi so'rovlar, EXECUTIONS, PARSE_CALLS, BUFFER_GETS, DISK_READS, ELAPSED_TIME. «Eng qimmat so'rovlar» shu yerdan topiladi.
  • V$SYSSTAT, V$SESSTAT: parse count (hard), physical reads, redo size kabi hisoblagichlar.
  • V$SGA, V$SGASTAT, V$PGASTAT: xotira taqsimoti.
  • AWR va ASH (10g dan, Diagnostics Pack litsenziyasi bilan): MMON jarayoni har soatda statistikani saqlaydi; AWR hisoboti ikki vaqt orasidagi farqni ko'rsatadi: eng ko'p kutilgan hodisalar (top wait events), eng qimmat SQL lar. ASH har sekund faol sessiyalarning surati.

5. AmaliyotdaTuzoqlar

Tuzoq: Java'da satr ulab yozilgan so'rov

stmt.executeQuery("SELECT ... WHERE hisob = '" + raqam + "'"). Testda bir foydalanuvchi, hammasi tez. Prodda sekundiga minglab chaqiruv: har biri qattiq parse, shared pool dagi latch va mutex uchun navbat (library cache: mutex X, latch: shared pool), CPU 100%, oxiri ORA-04031: unable to allocate shared memory. Ustiga SQL injection (P5).

To'g'risi: PreparedStatement va ?. Vaqtinchalik yechim sifatida CURSOR_SHARING = FORCE, lekin kodni tuzatish shart.

Tuzoq: siklda COMMIT

Har qator uchun COMMIT: har COMMIT da sessiya LGWR ning diskka yozishini kutadi (log file sync kutish hodisasi). Million qatorda million marta disk yozuvini kutish. Ustiga, yarim yo'lda xato bo'lsa, qayta ishga tushirish murakkab.

To'g'risi: mantiqiy birlik oxirida COMMIT; uzoq jarayonda bo'lak (masalan har 10 000 qator) oxirida, qayerdan davom etishni saqlab (P8).

Tuzoq: «hit ratio yaxshi, demak muammo yo'q»

Buffer cache hit ratio 99,9%, lekin tizim sekin. Sababi: bitta so'rov noto'g'ri reja bilan har chaqiruvda 2 million logical read qiladi. Hammasi keshda, shuning uchun nisbat a'lo, lekin CPU shunga ketyapti.

To'g'risi: nisbatlarga emas, kutish hodisalariga (AWR top events) va eng qimmat SQL larga (BUFFER_GETS, ELAPSED_TIME) qarash.

Tuzoq: har so'rovga yangi ulanish

Servis har HTTP so'rovda DriverManager.getConnection qiladi. Har ulanishda Oracle yangi server jarayoni yaratadi, autentifikatsiya, sessiya xotirasi: o'nlab millisekund va server resurslari. Yuklama oshganda «ulanish bo'roni» listener va serverni bosib qo'yadi.

To'g'risi: ulanishlar puli (HikariCP, UCP), cheklangan o'lcham bilan; bazada esa PROCESSES va SESSIONS chegarasini hisobga olish (P11).

Tuzoq: prodda «tezlashtirish uchun» ALTER SYSTEM FLUSH SHARED_POOL

Bitta so'rovning yomon rejasini tozalash uchun butun shared pool tozalandi. Keyingi daqiqalarda hamma sessiyaning hamma so'rovi qattiq parse qilinadi va paketlar qayta yuklanadi: tizim butunlay sekinlashadi.

To'g'risi: faqat bitta kursorni chiqarish (DBMS_SHARED_POOL.PURGE), yoki rejani barqarorlashtirish (SQL plan baseline, P7).

6. SuhbatdaSavol va namunaviy javoblar

Avval javobni o'zingiz ovoz chiqarib ayting, keyin oching. Bu mavzuda chizib tushuntirish (qog'ozda yoki doskada SGA, PGA va jarayonlar) juda kuchli taassurot qoldiradi.

Instance va database farqi nima?

Database bu diskdagi fayllar: datafile'lar (ma'lumot), online redo log'lar (o'zgarishlar jurnali), control file (tuzilma). Instance bu ularni ishlatadigan xotira (SGA) va fon jarayonlari. Instance ishga tushadi, control file ni o'qib bazani «mount» qiladi, keyin datafile'larni ochadi. Odatda bitta instance bitta bazani ochadi, RAC da bir nechta instance bitta bazani birgalikda ochadi. 12c dan multitenant: bitta CDB ichida bir nechta PDB.

SGA va PGA farqi? Har birida nima bor?

SGA hamma server va fon jarayonlari uchun umumiy xotira: buffer cache (ma'lumot bloklari), shared pool (SQL va PL/SQL kursorlari, rejalar, dictionary cache), redo log buffer, large pool, Java pool. PGA har server jarayonining xususiy xotirasi: sessiya ma'lumotlari, PL/SQL paket o'zgaruvchilari va kolleksiyalar, saralash va hash join uchun ish maydoni. SGA ni hamma ko'radi, PGA ni faqat o'z jarayoni. Shared server rejimida sessiya ma'lumotining bir qismi (UGA) SGA ga (large pool) ko'chadi.

Asosiy fon jarayonlari va ularning vazifasi?

DBWn: buffer cache dagi dirty bloklarni datafile'larga yozadi, to'plab va asinxron. LGWR: redo log buffer ni online redo log ga yozadi; COMMIT da, buffer uchdan bir to'lganda, har uch sekundda, DBWn yozishidan oldin. CKPT: checkpoint ni control file va datafile sarlavhalariga yozadi. SMON: instance ishga tushganda tiklashni bajaradi, vaqtinchalik segmentlarni tozalaydi. PMON: uzilgan sessiyaning tranzaksiyasini qaytaradi, qulflarini bo'shatadi. ARCn: ARCHIVELOG rejimida to'lgan redo log'larni arxivga ko'chiradi. MMON: AWR statistikasini yig'adi.

COMMIT bajarilganda ichkarida nima bo'ladi? Nega COMMIT tez?

Tranzaksiya davomida har o'zgarish uchun redo yozuvi redo log buffer ga tushadi, bloklar esa buffer cache da o'zgaradi. COMMIT da tranzaksiyaga SCN beriladi, commit yozuvi redo ga qo'shiladi va LGWR redo buffer ni online redo log fayliga yozadi. Sessiya faqat shu yozuvni kutadi (log file sync), keyin «commit complete». O'zgargan bloklar esa diskka hali yozilmagan bo'lishi mumkin, DBWn ularni keyinroq yozadi. COMMIT tez, chunki redo kichik va ketma-ket yoziladi, va COMMIT ning narxi tranzaksiya hajmiga deyarli bog'liq emas. Ishonchli, chunki redo diskda: yiqilishda undan bloklar tiklanadi.

Server yiqilsa commit qilingan ma'lumot qanday tiklanadi?

Instance recovery. Qayta ishga tushganda SMON control file dan oxirgi checkpoint ni topadi va online redo log ni shu joydan oxirigacha o'qib, hamma o'zgarishni bloklarga qayta qo'llaydi (roll forward): commit qilinganlar ham, qilinmaganlar ham, chunki undo o'zgarishlari ham redo da. Shundan keyin baza ochiladi va commit qilinmagan tranzaksiyalar undo bilan bekor qilinadi (rollback), bu fonda ham bajarilishi mumkin. Natija: hamma commit qilingan ma'lumot bor, commit qilinmaganlar yo'q. Checkpoint qanchalik yaqin bo'lsa, tiklanish shuncha tez (FAST_START_MTTR_TARGET).

Hard parse va soft parse farqi? Qattiq parse nega yomon?

Har SQL parse qilinadi: sintaksis, semantika (obyektlar, huquqlar), keyin SQL matnining hash i bo'yicha shared pool dagi tayyor kursor qidiriladi. Topilsa, soft parse: tayyor reja ishlatiladi. Topilmasa, hard parse: optimizator rejalarni baholab eng arzonini tanlaydi va yangi kursor yaratadi. Hard parse CPU ni ko'p sarflaydi va shared pool tuzilmalariga latch va mutex oladi, shuning uchun bir vaqtda ko'p sessiyada u parallel ishlamaydi va masshtablanmaydi; shared pool ni ham bir martalik kursorlar bilan to'ldiradi. Eng yaxshisi umuman parse qilmaslik: kursorni ochiq saqlab qayta bajarish; PL/SQL statik SQL buni o'zi qiladi.

Bind o'zgaruvchilar nima va nega muhim?

SQL matnidagi qiymat o'rniga belgi (:id yoki Java'da ?), qiymat esa alohida beriladi. Uch foydasi: SQL matni o'zgarmaydi, shuning uchun bitta hard parse va keyin soft parse, shared pool toza; SQL injection imkonsiz, chunki qiymat hech qachon kod bo'lib o'qilmaydi; ilova kodi soddaroq (qo'shtirnoq, sana formatlari muammosi yo'q). Kamchiligi: bind peeking tufayli notekis ma'lumotda bitta reja hamma qiymatga mos kelmasligi mumkin; 11g dan adaptive cursor sharing yordam beradi. Kam bajariladigan og'ir hisobot so'rovlarida literal ham qabul qilinadi.

Bind peeking va adaptive cursor sharing nima?

Bind peeking (9i): hard parse paytida optimizator bind ning haqiqiy qiymatiga qaraydi va shu qiymatga mos rejani tanlaydi, keyin shu reja hamma qiymat uchun ishlatiladi. Ma'lumot notekis bo'lsa (gistogramma bor), birinchi qiymatga qarab tanlangan reja boshqalar uchun yomon bo'lishi mumkin: so'rov ertalab tez, tushdan keyin sekin, chunki kursor shared pool dan chiqib qayta parse qilingan. Adaptive cursor sharing (11g): kursor bind ga sezgir deb belgilanadi, bajarilishlar kuzatiladi, va boshqa selektivlikdagi qiymat uchun yangi child kursor va reja yaratiladi. To'liq barqarorlik uchun SQL plan baseline.

CURSOR_SHARING=FORCE nima, qachon ishlatiladi?

Oracle o'zi SQL dagi literallarni tizim bind'lariga (:SYS_B_0) almashtiradi, shunda literal bilan yozilgan ilova ham kursorlarni bo'lishadi. Bu kodini tez o'zgartirib bo'lmaydigan ilova uchun vaqtinchalik dori. Kamchiliklari: hamma literal bind bo'ladi, hatto ataylab yozilgan (masalan holat = 'XATO' uchun maxsus reja kerak bo'lgan joyda), rejalar yomonlashishi mumkin; almashtirishning ham narxi bor. Sukut EXACT. Haqiqiy yechim ilovada bind.

Logical read va physical read farqi? Qaysi biri muhimroq?

Oracle blokni doim buffer cache orqali o'qiydi. Keshda bo'lsa logical read (consistent gets, db block gets), bo'lmasa diskdan keshga o'qiladi: physical read, keyin baribir logical read. Physical read sekinroq, lekin uning soni kesh holatiga bog'liq va o'zgaruvchan. Logical read so'rovning haqiqiy ishi: CPU va latch sarflaydi, va reja o'zgarmasa barqaror. Shuning uchun so'rovni tezlashtirishda logical read ni kamaytirishga harakat qilinadi; physical read o'z-o'zidan kamayadi.

Tizim sekin deyishdi. Qayerdan boshlaysiz?

Avval aniqlik: hammasi sekinmi yoki bitta ekran, qachondan, nima o'zgardi (reliz, ma'lumot hajmi, statistika). Keyin bazada: V$SESSION da faol sessiyalar nimani kutyapti (EVENT, SQL_ID, BLOCKING_SESSION); AWR yoki ASH hisobotida shu vaqt oralig'idagi top wait events va eng qimmat SQL lar. Kutish turi yo'nalishni beradi: db file sequential read (indeks orqali ko'p o'qish), log file sync (ko'p COMMIT), enq: TX - row lock contention (qulf, P8), library cache mutex (qattiq parse). Keyin aniq SQL ning rejasi va statistikasi (P7). Bitta o'zgarish, o'lchash, keyingisi.

7. Tekshiruv

Javoblarni chatga yozing.

  1. Doskaga Oracle arxitekturasini chizing: ilova, server jarayoni, PGA, SGA ning uch asosiy qismi, beshta fon jarayoni va uch xil fayl. Har strelkaga nima o'tishini yozing.
  2. Mijoz 1 million so'm o'tkazdi, «bajarildi» xabarini oldi, va bir sekunddan keyin server elektrdan o'chdi. Pul qayerda? O'zgargan bloklar diskka yozilmagan edi. Qadam-baqadam tushuntiring.
  3. V$SQLAREA da 40 000 ta SQL, matnlari faqat oxiridagi raqam bilan farq qiladi, har birida EXECUTIONS = 1. Nima bo'lyapti, qanday oqibat, kim nimani tuzatishi kerak?
  4. Hisobot so'rovi ertalab 2 sekund, tushdan keyin 3 daqiqa ishlaydi. So'rov bind bilan yozilgan, ma'lumot o'zgarmagan. Qanday gipoteza, qanday tekshirasiz?
  5. Kun yopishdagi katta GROUP BY so'rovi ORA-01652 bilan yiqildi. Bu nima degani va qanday yo'llar bor?

Chuqurroq

Consistent read: SELECT nega yozuvchini kutmaydi

SELECT boshlanganda SCN belgilanadi. Blok shundan keyin o'zgargan bo'lsa (yoki commit qilinmagan o'zgarish bo'lsa), server jarayoni undo dagi eski qiymatlardan blokning o'sha SCN dagi nusxasini keshda yasaydi va shuni o'qiydi. Shuning uchun o'quvchilar yozuvchilarni, yozuvchilar o'quvchilarni bloklamaydi. Undo yetmasa: ORA-01555: snapshot too old. Batafsil P8 da.

Session cursor cache va open_cursors

Ilova bir xil SQL ni yopib-ochib turaversa, har safar soft parse. SESSION_CACHED_CURSORS sessiya darajasida tez-tez ishlatilgan kursorlarga ko'rsatkichni saqlaydi, va soft parse yanada arzonlashadi («softer soft parse»). PL/SQL statik SQL kursorlarini o'zi ochiq saqlaydi (OPEN_CURSORS chegarasigacha). Java'da JDBC statement cache (setImplicitCachingEnabled, pul darajasida PreparedStatement keshi) xuddi shu vazifani bajaradi. ORA-01000: maximum open cursors exceeded odatda ilovada ResultSet yoki Statement yopilmaganidan.

Latch, mutex va kutish hodisalari

SGA dagi umumiy tuzilmalar (kesh zanjirlari, library cache) bir vaqtda bir necha jarayon tomonidan o'zgartirilmasligi uchun latch va 10g dan mutex bilan himoyalanadi. Ular juda qisqa ushlanadi, lekin talab juda ko'p bo'lsa navbat paydo bo'ladi: latch: cache buffers chains (bitta «issiq» blokni hamma o'qiyapti, odatda yomon reja yoki kichik jadvalga ko'p murojaat), library cache: mutex X (qattiq parse yoki bitta kursorga juda ko'p bajarish). Kutish hodisalari Oracle'da tahlilning asosiy tili: sessiya vaqti = CPU + kutishlar.

Multitenant, RAC va Data Guard bir jumlada

Multitenant (12c dan, 21c dan yagona arxitektura): bitta konteyner baza (CDB) ichida bir nechta ulanadigan baza (PDB), bitta instance va SGA ularning hammasiga. RAC: bir nechta server (instance) bitta umumiy diskdagi bazani birga ochadi, bloklar ular orasida tarmoq orqali (cache fusion) almashadi. Data Guard: asosiy bazaning redo si boshqa joydagi zaxira bazaga yuboriladi va qo'llanadi. Bank tizimlarida odatda Data Guard bor, ba'zan RAC.
