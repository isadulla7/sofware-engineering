1. Tezlikni tahlil qilish: senior birinchi navbatda shuni so'raydi

1. Sekin so'rovni tahlil qilish tartibi

Shifokor dori yozishdan oldin tahlil qiladi. "Ehtimol indeks kerakdir" deb darhol indeks qo'yish, tahlilsiz dori ichishga o'xshaydi.

Qoida: Tartib: 1) qaysi SQL sekin, aniq o'lchang (SQL_ID, vaqt, qatorlar); 2) haqiqiy rejani oling; 3) E-Rows va A-Rows ni solishtirib, qaysi qadamda vaqt ketganini toping; 4) sababini toping; 5) bitta narsani o'zgartiring; 6) qayta o'lchang va natijani raqam bilan yozing.

SELECT sql_id, executions, elapsed_time/1e6 sek, buffer_gets
FROM v$sql WHERE sql_text LIKE '%tolovlar%' ORDER BY elapsed_time DESC;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('&sql_id', NULL, 'ALLSTATS LAST'));

Qisqa javob: "Men taxmin qilmayman, o'lchayman: SQL_ID, haqiqiy reja, E-Rows va A-Rows farqi, keyin bitta o'zgartirish va qayta o'lchash."

2. AWR va ASH: "baza o'sha paytda nima bilan band edi"

Samolyotning qora qutisi: qulagandan keyin har daqiqada nima bo'lganini ko'rsatadi. AWR soatlik hisobot, ASH esa har soniyadagi surat.

Qoida: AWR ma'lum vaqt oralig'idagi eng og'ir SQL lar va kutishlarni ko'rsatadi. ASH (V$ACTIVE_SESSION_HISTORY) har soniyada faol sessiyalar nima qilayotganini yozadi. "Kecha 14:00 da sekinlashdi" degan shikoyatga shu bilan javob topiladi. Ikkalasi ham Diagnostics Pack litsenziyasini talab qiladi.

SELECT sql_id, event, COUNT(*) soniyalar
FROM v$active_session_history
WHERE sample_time > SYSDATE - 1/24
GROUP BY sql_id, event ORDER BY 3 DESC FETCH FIRST 10 ROWS ONLY;

Qisqa javob: "Muammo o'tib ketgan bo'lsa AWR va ASH dan qaysi SQL va qaysi kutish ko'p vaqt olganini topaman."

3. Wait events: sessiya nimani kutyapti

Ishchi ish vaqtining yarmida ishlaydi, yarmida material kutadi. Nimani kutayotganini bilsangiz, muammoni topasiz.

Qoida: DB time = CPU + kutish. Asosiy kutishlar: db file sequential read (indeks orqali bittalab o'qish), db file scattered read (full scan), enq: TX - row lock contention (birov qatorni qulflagan), log file sync (juda ko'p COMMIT), latch yoki mutex (ko'p hard parse).

SELECT event, total_waits, time_waited/100 sek
FROM v$system_event WHERE wait_class <> 'Idle' ORDER BY time_waited DESC;

Qisqa javob: "Kutish turiga qarab sababni aniqlayman: ko'p log file sync bo'lsa siklda COMMIT, row lock contention bo'lsa qulflar tartibi va uzun tranzaksiyalar."

4. Reja birdan o'zgardi: reja barqarorligi

Har kuni bir yo'ldan ishga borasiz, bir kuni navigator sizni aylanma yo'lga yubordi. Yo'l emas, navigatorning "bilimi" o'zgargan.

Qoida: Statistika yig'ildi, bind qiymati o'zgardi yoki versiya yangilandi: optimizator boshqa reja tanladi. Tezkor yechim: yaxshi rejani SQL Plan Baseline bilan mahkamlash. Keyin sababini topish: statistika, gistogramma, bind peeking.

-- yaxshi rejani kursor keshidan baseline ga yuklash
DECLARE n PLS_INTEGER;
BEGIN n := DBMS_SPM.LOAD_PLANS_FROM_CURSOR_CACHE(sql_id => '&sql_id', plan_hash_value => &yaxshi_plan); END;

Qisqa javob: "Reja regressiyasida avval yaxshi rejani SPM baseline bilan qaytaraman, keyin sababini statistika va bind lardan qidiraman."

5. Bind peeking va noteng taqsimlangan ma'lumot

Birinchi mijozga qarab butun do'konni sozlash: birinchi kelgan odam ulgurji xaridor edi, siz hamma uchun katta arava qo'ydingiz, oddiy xaridorlarga noqulay.

Qoida: Birinchi hard parse da optimizator bind qiymatiga qaraydi. Agar u kamdan-kam qiymat bo'lsa, reja hamma uchun noto'g'ri bo'ladi. Adaptive cursor sharing (11g) bunga qarshi bir nechta reja yaratadi; gistogramma noteng taqsimotni ko'rsatadi.

-- filial '01' da 5 million qator, boshqalarda 10 mingdan
SELECT ... FROM tolovlar WHERE filial = :f;   -- reja birinchi qiymatga bog'liq

Qisqa javob: "Ma'lumot noteng bo'lsa bind peeking yomon reja berishi mumkin; gistogramma, adaptive cursor sharing va kerak bo'lsa baseline bilan hal qilaman."

2. Katta hajm va to'xtovsiz ishlash

6. Parallel ishlash: kuchli, lekin umumiy resursni yeydi

Bitta katta xonani 8 kishi bilan bo'yash tezroq. Lekin 8 kishini boshqa xonalardan olib kelsangiz, ular to'xtab qoladi.

Qoida: PARALLEL hint yoki jadval darajasidagi parallellik katta full scan va yuklashni tezlashtiradi. OLTP vaqtida esa boshqa sessiyalarning CPU va diskini oladi. Tungi oynada, nazorat bilan ishlatiladi.

ALTER SESSION ENABLE PARALLEL DML;
INSERT /*+ APPEND PARALLEL(8) */ INTO arxiv SELECT /*+ PARALLEL(8) */ * FROM tolovlar WHERE sana < :d;

Qisqa javob: "Parallellikni tungi katta ishlarda ishlataman, kunduzgi OLTP da emas, va darajasini DBA bilan kelishaman."

7. Jadvalni to'xtatmasdan o'zgartirish

Uyni ko'chirmasdan ta'mirlash: odamlar yashashda davom etadi, ta'mir xonama-xona bo'ladi.

Qoida: Katta jadvalga NULL ustun qo'shish (yoki DEFAULT bilan, 12c dan) bir zumda. Indeksni CREATE INDEX ... ONLINE bilan qurish ish to'xtatmaydi. Tuzilmani butunlay o'zgartirish (partitsiyalash) uchun DBMS_REDEFINITION yoki ALTER TABLE ... MODIFY PARTITION BY ... ONLINE (12.2).

CREATE INDEX tolov_mijoz_ix ON tolovlar (mijoz_id) ONLINE;
ALTER TABLE tolovlar ADD (manba VARCHAR2(20));

Qisqa javob: "Prod da katta jadval o'zgarishini ONLINE amallar yoki DBMS_REDEFINITION bilan, test bazada vaqtini o'lchab, qilaman."

8. Partitsiya kalitini so'rovlarga qarab tanlash

Arxivni yil bo'yicha papkalarga bo'ldingiz, lekin hamma odam "mijoz bo'yicha" qidiradi: papkalar hech kimga yordam bermaydi.

Qoida: Kalit eng ko'p ishlatiladigan shartdan va tozalash usulidan kelib chiqadi: odatda sana (range yoki interval). Indekslar iloji boricha local. Global indeks kerak bo'lsa, partitsiya amallarida UPDATE INDEXES.

-- so'rovlar: WHERE sana BETWEEN ... AND filial = ...
PARTITION BY RANGE (sana) INTERVAL (NUMTOYMINTERVAL(1,'MONTH'))
SUBPARTITION BY LIST (filial) ...

Qisqa javob: "Partitsiya kalitini so'rovlar va arxivlash talabiga qarab tanlayman, aks holda pruning bo'lmaydi va partitsiya foyda bermaydi."

9. Og'ir hisobotni OLTP dan ajratish

Do'konning kassasida inventarizatsiya qilmaysiz: mijozlar navbatda qoladi. Inventarizatsiya omborda yoki kechasi.

Qoida: Katta hisobotlar uchun: materialized view (oldindan hisoblangan natija, belgilangan vaqtda yangilanadi), zaxira bazada (Active Data Guard) yoki DWH. Asosiy bazada esa qisqa tranzaksiyalar.

CREATE MATERIALIZED VIEW mv_kunlik_aylanma REFRESH COMPLETE ON DEMAND AS
SELECT filial, TRUNC(sana) kun, SUM(summa) jami FROM tolovlar GROUP BY filial, TRUNC(sana);

Qisqa javob: "Og'ir analitikani OLTP dan ajrataman: materialized view, zaxira baza yoki DWH."

3. PL/SQL dizayni: kod qanday qurilgan

10. Yagona xato va log tizimi

Har bo'limning o'z daftari bo'lsa, muammoni topish uchun 20 ta daftarni varaqlaysiz. Bitta umumiy jurnal bo'lsa, bir joyda ko'rasiz.

Qoida: Bitta log paketi: avtonom tranzaksiyada yoziladi, xato kodi, matn, FORMAT_ERROR_BACKTRACE, parametrlar va kontekst (foydalanuvchi, modul, hujjat id). Hamma joyda bir xil chaqiriladi.

EXCEPTION WHEN OTHERS THEN
  log_pkg.xato(p_modul => 'KREDIT', p_kontekst => 'kredit_id=' || p_id);
  RAISE;

Qisqa javob: "Jamoada bitta log paketi: avtonom tranzaksiya, backtrace va kontekst bilan, xato yutilmaydi, qayta ko'tariladi."

11. API dizayni: chaqiruvchi bilan shartnoma

Rozetka standarti: ichidagi simlar o'zgarsa ham vilka bir xil. Rozetkani o'zgartirsangiz, hamma jihozlar ishlamay qoladi.

Qoida: Spec barqaror bo'lsin: yangi parametr DEFAULT bilan qo'shiladi, eski chaqiruvlar buzilmaydi. API COMMIT qilmaydi, paket holatsiz, xato kodlari diapazoni hujjatlangan.

PROCEDURE berish(p_ariza_id IN NUMBER, p_summa IN NUMBER,
                 p_kanal IN VARCHAR2 DEFAULT 'EKRAN');   -- yangi parametr eski chaqiruvni buzmaydi

Qisqa javob: "API spec ni barqaror saqlayman: DEFAULT li yangi parametrlar, COMMIT yo'q, holatsiz paket, hujjatlangan xato kodlari."

12. Ikki marta bajarilmaslik (idempotentlik)

Liftning tugmasini besh marta bossangiz ham lift bir marta keladi.

Qoida: Tashqi tizim so'rovni qayta yuborishi mumkin (timeout). Har so'rovning tashqi identifikatoriga UNIQUE cheklov qo'yiladi: ikkinchi marta kelsa, yangi provodka emas, oldingi natija qaytadi.

ALTER TABLE tashqi_tolovlar ADD CONSTRAINT tt_tashqi_id_uk UNIQUE (manba, tashqi_id);
-- DUP_VAL_ON_INDEX bo'lsa: oldingi natijani qaytarish

Qisqa javob: "Pul bilan ishlaydigan har integratsiyada idempotentlik: tashqi id ga unique kalit va qayta so'rovda oldingi natija."

13. Navbatni parallel qayta ishlash

Bir nechta kassir bitta navbatga xizmat qiladi: har biri navbatdagi bo'sh odamni chaqiradi, bir odamni ikki kassir chaqirmaydi.

Qoida: FOR UPDATE SKIP LOCKED: har ishchi qulflanmagan qatorlarni oladi. Holat ustuni va urinishlar soni bilan, xato bo'lsa qatorni belgilab, keyingisiga o'tiladi.

SELECT id FROM navbat WHERE holat = 'YANGI' ORDER BY id
FETCH FIRST 100 ROWS ONLY FOR UPDATE SKIP LOCKED;

Qisqa javob: "Parallel ishchilar uchun SKIP LOCKED, har vazifa holati va qayta urinish hisobi bilan."

4. Xavfsizlik va ma'lumot himoyasi

14. Minimal huquq: jadvalga emas, API ga ruxsat

Bank xodimiga seyf kaliti emas, kassa dasturiga kirish beriladi: dastur qoidalarni o'zi tekshiradi.

Qoida: Ilova foydalanuvchisiga jadvallarga to'g'ridan-to'g'ri INSERT yoki UPDATE emas, faqat API paketlariga EXECUTE. Kod egasi sxemasi bilan ilova sxemasi alohida.

GRANT EXECUTE ON kredit_api TO app_user;
-- GRANT UPDATE ON hisoblar TO app_user;   -- bunday qilinmaydi

Qisqa javob: "Ilova faqat API paketlarini chaqiradi; jadvallarga to'g'ridan-to'g'ri huquq yo'q, shunda hamma qoida bir joyda tekshiriladi."

15. Shaxsiy va karta ma'lumotlari

Kassir mijozning karta raqamini to'liq ko'rishi shart emas: oxirgi 4 raqam yetarli.

Qoida: Karta raqami bazada shifrlangan, ekranda va logda maskalangan. Loglarga shaxsiy ma'lumot yozilmaydi. Oracle da buning uchun Data Redaction, TDE va VPD kabi vositalar bor (litsenziyaga bog'liq).

SELECT SUBSTR(pan, 1, 6) || '******' || SUBSTR(pan, -4) FROM kartalar;   -- 860002******1234

Qisqa javob: "Karta va shaxsiy ma'lumotni logga yozmayman, ekranda maskalayman, bazada shifrlangan holda saqlanadi."

5. Senior ning roli: kod emas, qarorlar

16. Kod review: nimaga qarash

Tajribali haydovchi yangi haydovchiga "tez yurding" demaydi, "bu burilishda oldin sekinla, chunki..." deydi.

Qoida: Ro'yxat: bind va injection, sikl ichida SQL, xatoni yutish, API ichida COMMIT, shartda partitsiya kaliti va indeks, qulflar tartibi, migratsiya va rollback, test va hujjat. Izoh "nega" bilan yoziladi.

-- review izohi: "Bu yerda siklda UPDATE bor, 300 ming qatorda 20 daqiqa.
--  Bitta UPDATE ... WHERE ... yoki FORALL bilan yozing."

Qisqa javob: "Review da xatoni ko'rsatibgina qolmay, sababini va to'g'ri usulni tushuntiraman: shunda jamoa o'sadi."

17. Trade-off ni tushuntirish

"Qaysi mashina yaxshi?" degan savolga senior "nima uchun kerakligiga qarab: shaharda kichigi, yuk uchun kattasi" deydi.

Qoida: Har yechimning narxi bor: denormallashtirish tezlik beradi, lekin sinxronlik talab qiladi; trigger qulay, lekin yashirin; parallel tez, lekin resurs oladi. Senior variantlarni narxi bilan aytadi va tanlovni asoslaydi.

-- qaror yozuvi: muammo, variantlar, tanlov, nega, oqibatlari

Qisqa javob: "Men "bu har doim yaxshi" demayman: har variantning foydasi va narxini aytaman, keyin aniq vaziyat uchun tanlayman."

18. RAC va Data Guard: dasturchi bilishi kerak bo'lgan qism

Bitta do'kon o'rniga ikkita filial: ikkalasi bitta omborga ishlaydi. Agar ikkalasi bir vaqtda bitta javondan olsa, bir-birini kutadi.

Qoida: RAC: bitta baza, bir nechta server. Hammasi bitta "issiq" blokni o'zgartirsa (masalan ketma-ket o'suvchi kalit indeksining oxiri) serverlar orasida tirbandlik. Sequence uchun CACHE katta, ORDER faqat kerak bo'lsa. Data Guard: zaxira baza, hisobotlarni shu yerda yurgizish mumkin.

CREATE SEQUENCE tolov_seq CACHE 1000;   -- RAC da NOCACHE yoki ORDER sekinlashtiradi

Qisqa javob: "RAC da issiq bloklar va sequence CACHE ni hisobga olaman; og'ir o'qishlarni zaxira bazaga beraman."

Senior ssenariy savollari

Senior darajasida ko'pincha "nima qilasiz?" degan vaziyat savoli beriladi. Avval o'zingiz ovoz chiqarib javob bering, keyin oching.

Kecha 5 daqiqa ishlagan job bugun 2 soat ishlayapti. Nima qilasiz?

Avval nima o'zgarganini aniqlayman, taxmin qilmayman. Job qaysi SQL da turganini ko'raman (V$SESSION dagi SQL_ID va event, ASH). Rejani oldingi bajarilish bilan solishtiraman (AWR dagi plan_hash_value): reja o'zgargan bo'lsa sababi statistika, bind yoki yangi indeks bo'lishi mumkin; tezkor yechim yaxshi rejani SPM baseline bilan qaytarish. Reja o'zgarmagan bo'lsa ma'lumot hajmi o'sganmi yoki kutish bormi (qulf, I/O). Topilgan sababni tuzataman, natijani raqam bilan yozaman va qayta bo'lmasligi uchun choralarni (statistika vaqti, monitoring) belgilayman.

2 milliard qatorli jadvalga yangi ustun va indeks kerak, ish to'xtamasin.

NULL li ustun qo'shish metadata amali, bir zumda (12c dan DEFAULT bilan ham). Indeksni CREATE INDEX ... ONLINE bilan, kerak bo'lsa PARALLEL bilan va keyin NOPARALLEL qilib quraman, partitsiyalangan bo'lsa LOCAL. Eski qatorlarni to'ldirish kerak bo'lsa: bo'laklab (DBMS_PARALLEL_EXECUTE yoki partitsiyalar bo'yicha), har bo'lak alohida commit va qayta ishga tushirishga chidamli. Avval test bazada vaqtini o'lchayman, DBA bilan oyna va rollback rejasini kelishaman.

Bitta to'lov ikki marta o'tib ketdi. Sababi va yechimi?

Odatiy sabablar: tashqi tizim timeoutdan keyin qayta yubordi va bizda idempotentlik yo'q; yoki ikki parallel ishchi bitta navbat qatorini oldi. Yechim: tashqi identifikatorga unique cheklov va qayta so'rovda oldingi natijani qaytarish; navbatda FOR UPDATE SKIP LOCKED va holatni bitta tranzaksiyada o'zgartirish; pul harakati va holat bitta COMMIT da. Keyin solishtiruv hisoboti bilan boshqa takrorlarni topib, storno qilinadi.

Kun yopishni 4 soatdan 1 soatga tushirish kerak.

Avval qaysi bosqich qancha vaqt olishini o'lchayman (har bosqich logi yoki ASH). Odatda vaqtni 2–3 ta bosqich oladi. Ularda: qatorma-qator sikl bo'lsa bitta SQL yoki BULK; filiallar bo'yicha parallel (DBMS_PARALLEL_EXECUTE yoki scheduler zanjiri); partitsiya pruning ishlayaptimi; siklda COMMIT va log file sync; keraksiz qayta o'qishlar. Har o'zgarishdan keyin qayta o'lchayman. Bosqichlarning bog'liqligini ko'rib, mustaqillarini parallel qilaman.

Review da WHEN OTHERS THEN NULL ko'rdingiz. Nima deysiz?

Xatoni yashirishini va qanday zarar berishini aniq misol bilan tushuntiraman: chaqiruvchi muvaffaqiyat deb o'ylaydi, yarim ish saqlanadi, sabab yo'qoladi. To'g'ri variantni ko'rsataman: kutilgan xatolarni nomi bilan ushlash, qolganini log paketi bilan yozib RAISE. Agar bu takrorlanadigan xato bo'lsa, jamoa qoidalariga va avtomatik tekshiruvga (masalan PL/SQL warnings yoki statik tahlil) qo'shishni taklif qilaman.

Hisobot so'rovi kunduzgi ishni sekinlashtiryapti.

Avval so'rovning o'zini tezlashtiraman: reja, pruning, keraksiz ustunlar. Yetmasa, hisobotni OLTP dan ajrataman: materialized view tungi yangilanish bilan, Active Data Guard zaxira bazasi yoki DWH. Resource Manager bilan hisobot foydalanuvchisiga CPU chegarasi ham qo'yish mumkin. Biznes bilan kelishaman: hisobot real vaqtda bo'lishi shartmi yoki kechagi holat yetadimi.

Trigger yoki API: qaysi birini tanlaysiz?

Biznes jarayoni (provodka, limit tekshiruvi, holat o'zgarishi) API protsedurasida: ochiq, test qilinadigan, BULK ni sekinlashtirmaydi. Trigger faqat har doim va istisnosiz bo'lishi kerak bo'lgan oddiy narsa uchun: audit, texnik ustunlar, tarix. Cheklov bilan yozsa bo'ladigan qoida (NOT NULL, CHECK, FK, UNIQUE) cheklov bilan yoziladi, trigger bilan emas.

Yangi modulning jadvallarini loyihalang: nimalarga e'tibor berasiz?

So'rovlar va hajmdan boshlayman: qaysi so'rovlar ko'p, qancha qator o'sadi, qancha saqlanadi. 3NF gacha normallashtiraman, ongli denormallashtirishni sabab bilan yozaman. Kalitlar: surrogate PK, natural kalitlarga UNIQUE, modul ichida FK. Turlar: pul NUMBER, kodlar VARCHAR2, sana DATE yoki TIMESTAMP. Katta jadvallar uchun partitsiya kaliti va local indekslar, arxivlash rejasi. Audit ustunlari, holat va operatsion kun, COMMENT ON va ER chizmasi.

Bu sahifadan olib ketadigan narsa. Taxmin emas, o'lchash: SQL_ID, haqiqiy reja, ASH va kutishlar. Katta hajmda ONLINE amallar va bo'laklab ishlash. Yagona log, DEFAULT parametrli API, unique kalit bilan idempotentlik, SKIP LOCKED navbat. Minimal huquq va niqoblash. Har qarorni trade-off bilan tushuntirish.
